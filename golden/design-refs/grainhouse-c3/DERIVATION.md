# DERIVATION — 시스템만으로 4개 화면을 그린 기록

실험: `_workspace/02_design/design-system/`(INDEX·principles·tokens·theme.code.css·components·
accessibility)만을 근거로 스캔 보관함·새 롤 접수·가격 안내·계정 화면을 생성했다.
승인 렌더는 열어봤으나 값을 복사하지 않았다 — 렌더 실측값(셀 17/14, 내비 42px, 갭 30/34)이
아니라 tokens.md의 정규화 토큰(16/12, 44, 32)을 썼다. 이 문서가 왕복(시스템 → 화면 → 부족
발견 → 시스템 갱신)의 데이터다.

## 2. 시스템에 없어서 새로 만든 것 — 시스템 갱신 후보

각 항목: 왜 필요했나 / 어느 원리로 결정했나 / 어느 절에 추가되어야 하나.

1. **표 필터 툴바(검색 + 셀렉트 + 결과 카운트)** — 보관함의 필터/검색 요구.
   B 폼 컨트롤을 표 위에 배치하고 결과 카운트를 mono data로 두는 조합(원리 3·5).
   → components.md B에 "테이블 툴바" 컴포넌트로 추가. 결과 카운트의 role="status"(스크린리더
   갱신 통지)도 계약에 포함할 것.
2. **테이블 밀도 변형(고밀도: 셀 상하 12px)** — ux-brief "표 밀도가 홈보다 높다"를 실현할
   장치가 토큰에 없음. 간격 허용 단계에서 12를 선택(원리 5).
   → tokens.md §간격에 "표 밀도 2단(기본 16 / 고밀도 12)"으로 명문화.
3. **빈 상태의 '괘선 유지' 구체 구현** — components.md B는 "grid 괘선 유지"라고만 말한다.
   그라데이션 금지(금지 목록) 때문에 repeating-linear-gradient 괘선 대신 실제 border 행
   (48px 빈 행 3개)을 썼다 — forced-colors 보존성도 이쪽이 낫다(accessibility.md §forced-colors).
   → components.md B 빈 상태 절에 구현 방식 확정 기록.
4. **오류 아이콘의 실물 형태** — "아이콘"이라고만 명세됨. 16px 정사각 + 1px error 보더 +
   mono "!"로 파생(원리 1: 잉크 테두리). → components.md B 폼 오류 절에 글리프·치수 확정.
5. **폼 폭** — 규정 없음. --size-prose-max(36em) 재사용(원리 5의 양식지=문서 여백 유추).
   → tokens.md §형태·구조에 폼 폭 규정(36em 재사용 또는 전용 토큰) 추가.
6. **폼 액션 행 규약** — 모달에만 "순서(보조·주)" 규정이 있음. 폼 하단 좌정렬 + 보조·주
   순서 + gap 16으로 일반화. → components.md B에 "폼 액션 행"으로 승격.
7. **파괴적 구역(danger zone) 패턴** — 파괴적 버튼만 있고 구획 패턴이 없음. 1px error 보더
   박스 + annot caps 제목 + body-sm 설명으로 파생(원리 2). → components.md B에 추가.
8. **warning의 데이터 셀 사용례(보관 만료 D-n)** — semantic 색의 표 내 사용 규약이 없음.
   "사건 발생 시에만"(원리 4)을 만료 임박에 적용, 항상 텍스트 동반. → components.md
   상태 절에 "만료/경고 주석" 사용례 추가.
9. **에러/파괴적 버튼의 hover 값 부재** — accent만 hover 토큰이 있다. 임의 색 파생은
   대비 미계산이라 하지 않고 hover 무변화로 뒀다(잉크는 이미 찍힌 값 — 원리 1과도 정합).
   → tokens.md 색 절에 "semantic hover는 의도적으로 없음" 또는 계산된 --color-error-hover 추가.
10. **페이지네이션 이전/다음 글리프(‹ ›)** — 숫자만 규정됨. mono 글리프 + aria-label로 파생
    (원리 3). → components.md B 페이지네이션 절 보강.

## 3. 새로 계산한 대비값

**없음 — 의도적으로.** 새 색을 하나도 만들지 않았다. 쓴 색·조합은 전부 accessibility.md
계산표에 이미 있는 값이다: warning/paper 5.17, warning/paper-2 4.72(행 hover 위 만료 주석),
error 보더 6.46/5.90(이중 배경 기능 보더 하한 통과), on-accent/error 7.41(파괴적 버튼).
semantic subtle-bg(color-mix 8%)는 "미계산 — 사용 승인 불가"라서 **어디에도 쓰지 않았다**
(알림 배너가 필요했다면 막혔을 것이다 — 이번 4화면에는 필요하지 않았다).

## 4. 불편했거나 모호했던 지점 (정직 기록 — 계약 개선 근거)

1. **한글 자간 금지 vs 렌더의 실천이 충돌한다.** tokens.md는 "한글에 양수 자간 금지 —
   tracking-*는 mono 라틴 caps 전용"이라 하는데, 정본인 승인 렌더의 readout 라벨("라인 상태",
   "금일 배치 마감")은 한글에 tracking 0.2em을 적용하고 있다. 폼 라벨·표 헤더도 한글이
   섞일 수밖에 없다. 우선순위 규칙(렌더=2위 > 원칙=4위)에 따라 렌더 관행을 따랐지만,
   시스템이 스스로 모순된다 — tokens.md가 "mono caps 마이크로 라벨은 한글 포함이라도 tracking
   허용(렌더 정본)"으로 정정되거나, 라벨의 한글 사용 자체를 규정해야 한다.
2. **micro(9.5px)의 'ink-2 전용' 제약이 semantic과 결합을 막는다.** danger zone 제목처럼
   overline 라벨에 error 색이 필요한 자리에서 micro를 못 쓰고 annot으로 올려야 했다.
   경계는 명확했지만(좋은 계약), "색이 ink-2가 아니면 한 단계 상향"이라는 파생 규칙을
   accessibility.md에 명문화하면 다음 사람이 고민하지 않는다.
3. **radius 0 "예외 없음"(tokens.md)과 "라디오=원"(components.md)이 문면상 충돌한다.**
   라디오를 원으로 그렸지만(components.md가 구체 스펙이므로 우선), tokens.md §형태에
   "예외: 라디오 버튼의 원형"을 명기해야 한다.
4. **readout 스트립이 어느 화면의 의무인지 불명.** 보관함에는 자연스러웠고 폼·문서·계정에는
   생략했다 — 판단 근거가 시스템에 없어서 원리 5(기록지인가 문서인가)로 정했다. layout 절이
   생기면 "기록지 화면 전용"으로 못 박을 것.
5. **"공정 4단계는 모든 화면에서 같은 언어"의 범위.** 계정 화면에는 공정 내용 자체가 없어
   미터를 넣지 않았다 — "공정이 등장하는 모든 자리에서 같은 언어"로 읽었다. ux-brief 하한의
   문구를 이 해석으로 정정할 필요가 있다.
6. **레일 CTA와 접수 화면의 중복.** 셸 스펙은 CTA를 포함하지만 접수 화면에서는 자기 자신을
   가리키게 된다. 원리 4로 생략을 정당화했지만 셸 계약에 "목적지 화면에서는 CTA 생략"을
   명문화해야 한다. CTA 서브라벨의 "마감 17:00"이 라이브 데이터라는 점도 셸 계약에서 다뤄야
   한다(어디서 갱신되나).
7. **hidden 속성과 display 유틸의 상호작용** — 페이지네이션을 display:flex로 선언하면
   hidden 속성이 무력화된다(실제로 첫 구현에서 버그). 컴포넌트 계약에 상태 숨김 방식
   ([hidden] 대응 규칙)을 포함하면 재발을 막는다.
8. **셀렉트 vs 라디오 판정 규칙은 좋았다** — "5개 이하 고정 집합이면 라디오"는 이번 폼에서
   전부 즉답을 줬다(포맷 3·현상 4·푸시 5·해상도 3·반송 3 = 라디오, 필름 10+ = 셀렉트).
   계약이 실제로 결정을 대신한 사례.
9. **접수 현황(홈) 링크 대상이 없다** — screens/에 홈이 없어 내비의 "접수 현황"을
   `_workspace`의 승인 렌더로 연결했다. 임시 조치이며 홈이 screens/로 옮겨지면 갱신 필요.

## 5. 총평 — 시스템은 충분했는가

**대체로 충분했다 — 그리고 부족한 곳도 예측된 자리에서만 부족했다.** 색·타입·간격·셸·표는
토큰과 A 스펙만으로 기계적으로 나왔고, 한 번도 임의 값을 만들 필요가 없었다(새 색 0개,
새 대비 계산 0건). B 스펙(폼·상태)은 "치수+원리" 수준의 명세였는데 실제 구현에서 즉답률이
높았다 — 특히 라디오/셀렉트 판정, 토글→체크박스 대체, 오류 3중 전달(보더+아이콘+메시지)은
계약이 그대로 코드가 됐다. 원리 5개는 실제로 결정 기능을 했다: 이 문서의 "파생" 행 전부가
특정 원리 번호로 환원된다(가장 많이 쓴 것은 원리 4·5).

남은 갭은 §2의 10건이며 전부 컴포넌트/패턴 수준이지 토큰·원리 수준이 아니다. 즉 시스템의

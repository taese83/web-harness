# 티켓 준비도 게이트 — 설계안 (미적용)

*2026-09-08 · 상태: **제안**. 코드·계약 미수정.*
*개정 2 — 자리를 옮겼다: 「기획 단계 validator」가 아니라 **티켓 필드 준비도가 개발 착수를 막는
게이트**다. 개정 1의 C1·C3은 §5에서 폐기한다.*

---

## 0. 대상 흐름

```
기획자가 기획서 작성 → 업로드
   → feature 추출
   → feature마다 분석: 추가로 필요한 것 + TC 생성
   → 티켓 발행(Jira) — AI가 개발할 정보 + 기획자가 읽는 템플릿
      (1 FEAT = 1 티켓이 아니라 더 쪼갤 수 있음)
   → 기획자가 티켓의 빈 항목을 채움 (예: Figma 링크)
   → 개발자가 team-flow에서 픽업
      → 항목이 안 채워졌으면 **BLOCK**, 보충해야 진행
```

---

## 1. 결론 — 대부분 이미 있다. 없는 것은 셋이다

| 흐름 단계 | 상태 | 근거 |
|---|---|---|
| 기획서 → feature 추출 | **있음** | `source-artifact-ingestor` → `requirements-analyst` → `feature-planner` |
| feature마다 TC 생성 | **있음** | `feature-planner` 16-1 — Must FEAT마다 동작 명세 + `TC-NNN-N`, REQ AC를 정본으로 재사용 |
| 티켓 발행(Jira) | **있음** | `team-flow` claim + `provider-jira.mjs`. 원장에 `FEAT ↔ 티켓키 ↔ PR` |
| 개발 착수 게이트 | **있음** | `pickupTicket` — fail-closed bounce 구조가 이미 있다 |
| **① 티켓 내용 준비도가 픽업을 막는 배선** | **없음** | §2 — 필드는 있는데 게이트가 안 읽는다 |
| **② 기획자가 채울 필드 스키마** | **없음** | §3-1 — 어휘가 하드코딩 3개뿐 |
| **③ feature 1:N 세분화** | **없음** | §3-2 — 계약엔 있고 파서가 못 읽는다 |

**새로 만들 것은 거의 없다. 안 이어진 선을 잇는 일이다.**

## 2. 핵심 발견 — `specCompleteness`는 있는데 pickup이 안 읽는다

`NormalizedTicket`에 이미 필드가 있고, 이름이 정확히 **"개발 진입 준비도"**다.

`normalize.mjs:24`
> `@property {{ready, missing}} specCompleteness` **개발 진입 준비도**

`normalize.mjs:70`
> 개발 진입 준비도 — **pickup(단계 3)이 이 판정으로 되돌림 여부를 결정한다.**

**그런데 결정하지 않는다.** `specCompleteness`의 소비자 전수:

| 소비 지점 | 무엇을 하나 |
|---|---|
| `emit.mjs:123` | 미리보기에 `⚠ 스펙 미완(...)` 문자열 |
| `runner.mjs:122` | `specWarning` 필드로 전달 |
| `batch-claim.mjs:58` | 보드에 `specReady` 표시 |

셋 다 **표시**다. `pickup.mjs`는 이 필드를 **한 번도 읽지 않는다.**

`pickupTicket`이 실제로 막는 것은 셋뿐이다:

1. `injection-suspect` — 본문 인젝션 의심
2. `spec-incomplete` / `unknown-feature` — `reconcileWithPlan`이 보는 것은 **FEAT/TC 참조 정합성만**
   (featureId 존재 · plan에 그 FEAT 존재 · TC 참조 ≥1 · TC가 plan TC 집합에 속함)
3. `plan-out-of-sync` — 청구 해시 ≠ 로컬 해시

즉 **본문(behavior)이 비어 있어도 FEAT/TC 스탬프만 맞으면 픽업이 통과한다.**
`emit.mjs:23`이 스스로 적어둔 그대로다: "specCompleteness로 스펙 완결성만 보고(**게이트 안 함**)".

> 이것은 이 저장소에서 **세 번째 「기계 소비자 0」**이다 — Gate B의 routeBinding(`fc8e670`이 닫음),
> `QUESTION(Q-NNN)` 마커(미해결), 그리고 이것. 다만 앞의 둘과 다르게 **주석이 배선을 이미
> 약속하고 있다**("pickup이 이 판정으로 결정한다"). 약속과 실제가 어긋나 있으므로 **I1 문제**다.

## 3. 없는 것 셋

### 3-1 · 기획자가 채울 필드 스키마가 없다

현재 `missing` 어휘는 두 곳에 **하드코딩된 3개**다:

```
behavior · acceptanceCriteria · testCaseIds     (emit.mjs:30-32, normalize.mjs:82-84)
```

말씀하신 **Figma 링크**·화면 상태·문구·권한 규칙 같은 것이 들어갈 자리가 없다. 그리고 지금
어휘는 전부 **하네스가 채우는 것**이라 "기획자 몫"이라는 개념 자체가 없다.

필요한 것:

- 필드를 **선언으로** 둔다 — `requestType`(feature/bug/task…)별 필수 필드 목록.
  `pickupTicket`이 이미 `requestType`을 인자로 받는다(배선 지점이 이미 있음)
- 필드마다 **`owner: planner | harness`** — 누가 채우는가
- **I3 주의**: 필드 목록을 코드에 박으면 특정 서비스 인코딩이다. 프로필 선언이어야 하고,
  기본값은 최소로 둔다(예: `figmaUrl`은 `DESIGN_SOURCE`가 선언된 프로필에서만 필수)

### 3-2 · feature 1:N 세분화가 안 된다

계약에는 이미 있다 — `design-readiness-contract.md` §3-2의 `FEAT-NNN-NN` 하위 기능 표
(`feature-planner` 16-2: "독립적으로 설명·검증·변경 가능한 행동이 둘 이상이면").

**그런데 티켓 파서가 못 읽는다.** `plan-units.mjs:17`이 스스로 적어뒀다:

> **오수집**된다(`FEAT-001-01` → `featureId=FEAT-001`, `title="01 …"`). 과소(미수집) 방향이 정직.

그리고 emit의 원장 앵커가 `sourceKey: unit.featureId`라 **1 FEAT = 1 티켓으로 고정**돼 있다.
1:N으로 가려면 앵커를 하위 기능 ID로 내려야 하고, 그것은 **멱등 emit·stale 판정·PR 링크·보드
집계 전부**에 영향을 준다.

> **이 요청에서 가장 큰 구조 변경이다.** §4에서 별건으로 분리할 것을 권고한다.

### 3-3 · 기획자에게 되돌아가는 길이 없다

`TicketProvider`는 `resolve` / `emit` / `update` 셋이고, `update`는 하네스 → 트래커 방향
(status·prUrl·evidence)이다. **"무엇이 비었으니 채워달라"가 기획자에게 가는 경로가 없다.**

배선 없이 §2만 고치면 결과는 이렇게 된다 — **개발자가 막히고, 거기서 끝난다.** 기획자는
막힌 사실을 모른다. 게이트를 세우기 전에 이 왕복이 있어야 한다.

## 4. 제안 — 3단, 순서대로

### S1 · pickup에 `content-incomplete` 판정을 잇는다 *(가장 값싸다 · 즉시 가능)*

`pickupTicket`의 bounce 순서에 하나를 추가한다:

```
injection-suspect → spec-incomplete/unknown-feature
  → [신설] content-incomplete   ← ticket.specCompleteness.ready === false
  → plan-out-of-sync → ok
```

bounce에 `missing` 목록을 실어 개발자에게 **무엇이 비었는지** 그대로 보인다.

- **새 기능이 아니다.** `normalize.mjs:70`이 이미 약속한 배선을 잇는 것뿐이다
- 지금 어휘(behavior/AC/TC) 그대로도 의미가 있다 — 본문 없는 티켓이 픽업되는 것을 막는다
- **반증 1건으로 증명된다**(§6). 실제 기획서가 필요 없다

### S2 · 필드 스키마 + 기획자 왕복

- `requestType`별 필수 필드 선언(`owner: planner|harness`)
- 발행 본문에 미충족 필드를 **빈 체크박스**로 남긴다 → 기획자가 Jira에서 그 자리에 채운다.
  별도 도구를 안 배워도 되고, 티켓이 곧 질문지다
- 픽업 시 `provider.resolve()`가 그 체크박스를 다시 읽어 `specCompleteness`를 재계산
- **BLOCK 시 티켓에 코멘트로 미충족 목록을 남긴다** — §3-3의 되돌아가는 길

### S3 · 세분화 *(별건)*

선행 조건이 둘이다: ① `plan-units.mjs`의 `FEAT-NNN-NN` 오수집 수정 ② 원장 앵커를 하위 기능
ID로 내리는 마이그레이션. **S1·S2와 같이 하면 안 된다** — 앵커 변경은 이미 발행된 티켓의
청구를 무효화할 수 있고, 그 사고가 이 저장소에 실측 기록으로 남아 있다(`emit.mjs:52` —
"선언 커밋 하나로 11건이 영구 픽업 불가").

## 5. 개정 1(모호성 게이트)의 처분

| 개정 1 대조 | 처분 |
|---|---|
| C1 · 질문 증발(gap-report ↔ 질문지) | **폐기.** 티켓 빈 필드가 질문지 역할을 대신한다 — 기획자가 이미 쓰는 도구 안에 있고, 안 채우면 **개발이 실제로 막힌다**. `author-questions.md`보다 강하다 |
| C2 · 막음 ↔ BLOCKER 비대칭 | **흡수.** 티켓 BLOCK과 같은 축이다. 필드 미충족이 곧 `막음`이다 |
| C3 · 하류 마커 생존 | **폐기.** 마커로 표시할 이유가 없다 — 미충족 필드가 직접 막는다 |

**개정 1의 접근이 약했던 이유가 이제 분명하다.** 그쪽은 문서에 표시를 남기고 사람이 읽기를
기대했다. 이쪽은 **개발 착수라는 실제 사건을 막는다.** 후자가 이 저장소의 기존 규율
(proof-gated)과 같은 등급이다.

## 6. 평가 방법 — 지난번 순환이 여기서는 안 생긴다

지난 실측이 무효였던 이유는 하네스가 입력을 쓰고 산출물을 쓰고 그것을 잰 순환 때문이었다.
이 설계는 다르다:

| | 증명 대상 | 필요한 것 | 순환하나 |
|---|---|---|---|
| S1 | 배선 — 미충족 티켓이 픽업에서 막히는가 | **반증 변이 1건** + 단위 테스트 | 아니오 |
| S2 | 탐지력 — 빈 필드를 잡는가 | **적대 fixture**(필드 하나를 비운 티켓 본문) | 아니오 |
| S2 | 유의미성 — **필드 목록이 맞는가** | **실제 Jira 티켓과 기획자의 실사용** | — |

S1·S2의 앞 두 줄은 지금 바로 가능하다. 세 번째 줄만 사용자 실사용이 필요하고, 그것은
`workspace/*` 프로브로 대체할 수 없다(대체하려는 시도가 개정 1의 오류였다).

## 7. 불변식 대조

| | 답 |
|---|---|
| **I1** | §2가 "주석이 약속한 배선이 없다"를 근거와 함께 적었다. S1은 없던 것을 만드는 게 아니라 어긋난 것을 맞추는 일이며, 그 사실을 과장하지 않는다 |
| **I2** | 게이트를 **강화**한다. 지금 통과하던 것(본문 없는 티켓)이 막힌다 |
| **I3** | 필드 목록을 코드에 박지 않고 `requestType`별 선언으로 둔다(§3-1). Jira 고유 개념을 코어에 넣지 않는다 — `TicketProvider` 뒤에 둔다는 기존 규율 그대로 |
| **I4** | 신규 의존성 0. S1은 기존 순수 함수에 판정 하나 추가. 스킬·always-read 표면 증가 없음 |
| **I5** | 필드 **존재**는 내용 품질의 프록시다 — 빈 체크박스에 "확인함"만 적어도 통과한다. §8-2의 결정 사항이며, 승격 시 §4 등록부에 구멍으로 기재 |
| **I6** | 접근성·보안·receipt 경로 불변. 인젝션 격리(`quarantineExcerpt`)는 그대로 앞단에 남는다 |

## 8. 결정이 필요한 것

1. **S1만 먼저 갈 것인가** — 배선 하나라 작고, 지금 어휘로도 즉시 값이 난다. 권고: 예
2. **필드 목록 초안을 무엇으로 잡을 것인가** — 실제 Jira 화면의 필드 구성이 있어야 정한다.
   기획 템플릿(`docs/planning-document-template.md`)의 「화면마다 / 기능마다」 항목을 그대로
   티켓 필드로 내리는 안이 자연스럽다
3. **세분화(S3)를 이번 범위에 넣을 것인가** — 권고: 아니오(앵커 마이그레이션 별건)

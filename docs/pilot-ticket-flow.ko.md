# 팀 흐름 실측 (1단계)

사람이 만든 개발 티켓 흐름(판정 · 가정 출구 · 티켓 키 선행 · 겹침 확인 · `create`)을 실제 팀 티켓으로 돌려 **막히는 지점과 설계 결함**을 찾는다.
표본이 작고 비교군이 없으므로 이 실측으로 생산성 효과를 주장하지 않는다.

## 진행

- 대상: 실제 팀의 공통 로직 개발 티켓 한 묶음(첫 대상은 aoa-web 9건). 가능하면 1~2건은 하네스 저자가 아닌 팀원이 진행한다.
- 흐름은 평소대로 — `pickup` → 판정 → 확인 → 개발 → `link` → 머지. 실측을 위해 따로 하는 일은 없다.
- 하네스가 막으면 게이트를 고치지 않고 데이터 쪽으로 뚫은 뒤, 막힌 사실과 우회를 한 줄로 적는다(흐름 로그가 멈춤은 자동으로 남긴다).
- 준비: 플러그인 0.37.0 이상, 개발 준비 검사 `--fix`(로컬 기록 git 제외). `.gitignore`에 흐름 로그 줄이 없으면 기록하지 않고 결과에 그 사실을 알린다.

## 기록과 집계

- `pickup`·`link`·`create`가 결과를 `_workspace/03_dev/flow-log.jsonl`(로컬, git 제외, 전송 없음)에 자동으로 남긴다.
- 끝나면 `team-flow pilot-report [--keys …]` — 흐름 로그·판정서·등록·연결 기록과 트래커 상태·코멘트·머지된 PR을 티켓별 표로 잇는다(읽기만).
- 머지 뒤 2주가 지나면 다시 돌리고, 그 티켓을 원인으로 한 결함 수를 사람이 더한다.

## 미리 정한 판단 규칙

결과를 본 뒤 해석을 맞추지 않도록 먼저 정한다.

| 관측 | 행동 |
|---|---|
| 기획 필요 판정의 절반 이상이 「완료 조건을 관찰 가능하게 못 씀」 | 판정이 아니라 티켓 양식 안내를 고친다 |
| 가정을 쓴 티켓 중 기획자 정정이 30% 초과(답글을 사람이 읽어 판정) | 가정 출구 범위를 좁힌다 |
| 겹침을 확인한 건에서 실제 머지 충돌 발생 | write 에이전트 worktree 격리를 앞당긴다 |
| 7/9 이상이 하네스 수정 없이 착수 | 흐름 합격 — 실행 가능한 완료 조건(2단계)으로 간다 |
| 사람이 우회한 경우 1건 이상 | 원인을 분류해 보고서에 싣는다 |

## 한계

- 집계는 기록의 모양만 잇는다 — 판정의 참, 답글이 정정인지 동의인지, 우회 여부는 사람이 읽는다.
- 티켓별 토큰 비용은 없다(스폰 텔레메트리는 run 단위이고 오케스트레이터가 계약을 따라 적는 방식이라 빠질 수 있다).
- 흐름 로그와 판정 기록은 개발자 로컬이다 — 여러 사람이 진행하면 각자의 클론에서 집계하거나 기록을 모은다.

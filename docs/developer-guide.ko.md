# 개발자 가이드 — 티켓으로 개발할 때 web-harness 쓰는 법

팀 프로젝트에서 **티켓 하나를 받아 PR로 끝내기까지** 하네스를 어떻게 쓰는지 정리한다. 괄호 안의 CLI 명령은 무엇이 실행되는지
알려 주는 참고다 — 직접 칠 필요는 없다.

> **처음 한 번 `/web-harness:wh`로 시작한다 — 그다음부터는 평문으로 말하면 된다.**
> 하네스 스킬은 모델이 스스로 부르지 못한다(의도치 않은 발동을 막는 설계). 그래서 세션을 `/web-harness:wh`로 시작하면(인자 없이
> 부르면 무엇을 할지 묻는다) 그 세션·그 프로젝트가 **하네스 모드**가 되고, 이후 "AOA-70 픽업", "설정 화면 저장 버튼이 두 번 눌려" 같은 평문 요청도
> 하네스가 티켓 작업·레인(fix/change…)으로 가려 처리한다. 하네스와 무관한 질문은 그냥 답한다. 끝낼 때는 `/web-harness:wh off`.
> - 하네스 모드는 매 요청에 라우팅 문서 경로를 안내로 붙이는 방식이다(훅). 모델이 따르는 안내라 100% 보장은 아니다 — 하네스로
>   처리되지 않은 것 같으면 그 요청만 `/web-harness:wh <요청>`으로 다시 보내면 된다.
> - 새 세션을 열면 다시 `/web-harness:wh`로 켠다(`--resume`으로 이어 간 세션은 유지된다).
> - 티켓 작업은 `/web-harness:team-flow <요청>`으로 바로 시작해도 되고, 이것도 하네스 모드를 켠다.

기획·디자인이 **있어도 없어도** 같은 흐름이다. 달라지는 것은 티켓을 누가·어떻게 만드느냐뿐이다.

```
준비(한 번) → 티켓 만들기 → pickup(판정·확인) → 개발 → PR 전 리뷰 → link → PR → 머지
```

---

## 1. 준비 — 처음 한 번

| 할 일 | 방법 | 비고 |
|---|---|---|
| 플러그인 설치·업데이트 | `/plugin marketplace add https://github.com/taese83/web-harness-plugin` → `/plugin install web-harness@web-harness-marketplace` (HTTPS가 막힌 망이면 `git@github.com:taese83/web-harness-plugin.git`) | 업데이트는 `/plugin`에서. 새 버전은 **새 세션**부터 적용된다. 계약 사본(`_workspace/.contracts/`)은 세션 시작 때 자동으로 맞춰진다 |
| 트래커 설정 | "트래커 설정해줘" (`configure --provider jira`) | 팀에 한 번. 설정 파일 `_workspace/03_dev/ticket-provider.json`은 커밋된다. **토큰은 파일이 아니라 환경변수**(`JIRA_TOKEN`) |
| 개발 준비 검사 | "개발 준비 검사해줘" (`validate-development-readiness.mjs --project . --fix`) | 개발자 로컬 기록(판정서·연결 기록·흐름 로그)의 git 제외와 원장 병합 규칙을 넣는다 — **팀 저장소를 바꾸므로 한 사람이 PR로 한 번**. 이미 들어가 있으면 할 일이 없다 |
| (선택) 내 리뷰 설정 | 홈 디렉터리의 `.claude` 폴더 아래 `web-harness/local.json` | 저장소를 고치지 않고 **나에게만** PR 전 리뷰어·참고 문서를 더한다 — 아래 6절 |

팀 전체가 같아야 하는 설정(개발 티켓 컴포넌트·라벨, 제목 접두어 `titlePrefix`, 팀 리뷰어 `reviewAgents`)은
트래커 설정에 둔다. 저장소를 고칠 수 없으면 제목 접두어는 초안 제목에 직접 쓰고, 리뷰어는 로컬 설정으로 더한다.

## 2. 티켓 만들기

### 기획이 있을 때 — 계획 WORK
기획(`feature-plan`)과 스팩이 있으면 "개발 준비해줘"(`claim`) → 분해안 검토 → "티켓 발행해줘"(`claim --publish`, 미리보기 뒤 확인).

### 기획·디자인이 없을 때 — 개발 티켓 (`create`)
"공통 로직을 개발 티켓으로 나눠줘"처럼 요청한다. 하네스가 코드와 스팩을 읽고 초안을 쓴다
(`_workspace/03_dev/ticket-drafts/<이름>.md`) → **미리보기를 보고 확인**하면 트래커에 만든다.

초안 양식 — 사람이 직접 쓰는 개발 티켓도 같은 양식을 쓴다.

```markdown
## [FE] 홈 화면 최근 본 항목 섹션
### 목적
한 문장. 근거가 있으면 `근거:` 한 줄(또는 끝의 선행·협의에 `상세기획:`·`디자인:` 링크)
### 수정 범위            ← 선택
- src/pages/home/
### 작업 내용
- 무엇을 어디에 만드는지
### 하지 않는 것          ← 선택
- 범위 밖과 한 줄 이유
### 완료 조건
- 확인할 수 있는 결과만("~한다"). 의도 문장("~할 수 있게 한다")은 쓰지 않는다
### 선행·협의
- 선행: AOA-60 (또는 같은 초안의 제목)
- 협의: 미정인 것 — 가정안
```

- 필수는 목적·작업 내용·완료 조건·선행·협의 네 절이다. FEAT·TC ID는 쓰지 않는다(계획 WORK의 몫).
- 같은 제목의 열린 개발 티켓이 있으면 새로 만들지 않고 그 키를 알려 준다.
- **이미 끝낸 작업은 다시 만들지 않는다.** 초안 에이전트가 요청과 같은 일을 하는 기존 코드·스팩 결정을 먼저 찾아, 겹치면 차이만
  티켓으로 쓰거나(선행·협의에 `겹침:`) 만들지 않고 그 위치를 알려 준다. 미리보기에는 **최근 끝난 개발 티켓 목록**이 함께 나온다 —
  같은 일을 이미 끝낸 티켓이 보이면 확인하지 않는다(끝난 티켓과의 겹침은 기계가 막지 않고 사람이 가린다).
- 다른 개발자·AI가 따라 쓸 **공통 로직** 티켓이면 완료 조건에 그 강제 수단(공통 팩토리, lint 규칙, 모듈 사용법 문서, 스팩 결정 기록)을
  넣는다. 개발 에이전트가 매번 읽는 것은 스팩·규약 문서이고, 실제로 지켜지게 하는 것은 lint다.

### 사람이 직접 만든 티켓
트래커에서 팀의 **개발 티켓** 분류(Jira 컴포넌트·GitHub 라벨)로 만들면 그대로 `pickup`할 수 있다.

## 3. 티켓 집기 — `pickup`

"AOA-65 픽업"(`pickup AOA-65 --developer me`). 순서는 **배정 → 판정 → 확인**이다.

1. **나로 배정**한다. 이미 남이 배정돼 있으면 멈춘다.
2. 하네스가 티켓을 **판정**한다.

   | 판정 | 뜻 | 다음 |
   |---|---|---|
   | 착수 가능 (`fix` / `change`) | 완료 조건·테스트 항목(`TT-키-n`)·수정 범위를 제안한다 | 미리보기를 보고 **확인** |
   | 기획 필요 | 새 사용자 흐름·정책(권한·금액·삭제·상태 전이)을 정해야 한다 | 요청 코멘트를 확인하면 티켓에 남긴다 |
   | 디자인 필요 | 새 화면·모양이 정해지지 않은 새 상태 | "디자인은 임의로 해" 지시가 있으면 착수 가능으로 다시 판정 |
   | 판정 불가 | 스팩이 없거나 수정 범위가 스팩 `layerMap` 밖 | 스팩에 소유를 추가(스팩 재확정 PR)한 뒤 다시 |

3. **확인하면** 이 판정이 곧 그 작업의 기준이다. AI가 제안한 완료 조건은 확인 전까지 기준이 아니다.
   - 새 route·데이터 계약처럼 동작을 새로 정의하는 티켓(`specApproval: required`)은 구현 전에 스팩 승인을 한 번 더 받는다.
     기획 없는 프로젝트여도 **결정 로그(PC-NNN)를 새로 만들지 않는다** — 확인한 완료 조건이 그 라운드의 기준이다.
   - 기획이 안 정한 세부를 가정했거나 디자인을 임의로 정하면, 그 사실을 티켓 코멘트로 알린다(기획자·디자이너가 바로잡을 수 있게).

## 4. 개발

- **dev 브랜치**를 따서 개발한다. 브랜치 이름에 티켓 키를 넣는다(`feature/AOA-65-recent-items`) — PR 제목(`[AOA-65] …`)이나 브랜치 중
  하나에 키가 있어야 `link`와 완료 판정이 그 PR을 찾는다. 커밋·dev 브랜치 push는 묻지 않고 진행하고, **PR 직전에 한 번 확인**받는다.
- 수정은 픽업이 정한 **수정 범위** 안에서만 한다 — 하네스 개발 에이전트는 범위 밖에 쓰지 못한다(훅이 막는다).
  범위를 넓혀야 하면 멈추고 판정을 다시 받는다.
- 테스트 코드에 테스트 항목 ID(`TT-AOA-65-1`)를 인용한다 — 연결(`link`)이 인용을 확인한다.
- **사용자 흐름(화면 이동·탭 전환 등)을 바꾸는 작업이면 e2e 테스트**를 스팩의 `testLayers.e2e` 경로에 더한다.
  하네스는 e2e를 강제하지 않지만, 없으면 PR 전 리뷰가 그 사실을 적는다.
- 팀 규약 문서(`AGENTS.md` 등)는 하네스 기본 규약보다 앞선다. 스팩 `constitution.conventions`에 등록돼 있으면 개발·리뷰
  에이전트가 읽는다.

## 5. PR 전 리뷰

"PR 연결 미리 봐줘"(`link <키> <pr-url> --dry-run`) → 결과의 `review`대로 리뷰한다.

- **하네스 리뷰어**(`web-harness:code-reviewer`)는 늘 돈다. 팀 설정 `reviewAgents`나 내 로컬 설정의 **프로젝트 리뷰어**
  (예: 저장소의 `code-reviewer`)도 **같은 범위**(`review.base`...`review.head`)로 돈다.
- 리뷰 범위는 **diff와, diff가 바꾼 것을 쓰는 연관 코드**다. 연관 코드에서는 이번 변경 때문에 생긴 문제(깨진 호출부,
  바뀐 동작에 기대던 곳, 남은 고아 참조)만 보고하고, base에 원래 있던 문제는 보고하지 않는다.
- 고칠 결함은 고치고 다시 리뷰한다. 리뷰 결과·TC/check 결과·남은 미결을 보고 **확인하면 PR을 만든다**.

## 6. 연결과 완료 — `link`

"AOA-65를 PR #31에 연결"(`link AOA-65 <pr-url>`).

- 완료 조건 충족·수정 범위 변화·테스트 항목 인용·**PR 제목이나 브랜치의 티켓 키**를 확인한다. 미충족이면 막는다
  (넘기면 그 사실이 기록과 PR 본문 문단에 남는다).
- 결과의 `prBody` 문단을 PR 본문에 넣는다(리뷰어가 볼 인수 사항·닫는 줄).
- **완료는 머지로 판정한다** — 기대 base에 머지된 PR을 제목·브랜치의 티켓 키로 찾는다. Jira 티켓은 머지로 자동 닫히지 않는다.

### 내 리뷰 설정(로컬, 선택)

저장소를 고칠 수 없을 때, 홈 디렉터리의 `.claude` 폴더 아래 `web-harness/local.json`:

```json
{"projects": {"/Users/me/Project/aoa-web": {
  "reviewAgents": ["code-reviewer"],
  "reviewReferences": ["docs/conventions.md", "docs/react.md", "docs/testing.md"]
}}}
```

키는 프로젝트 **절대 경로**, 받는 것은 이 둘뿐이다. 참고 문서는 프로젝트 안 파일만. 결과의 `review.local`에 출처가 남는다.

## 7. 자주 멈추는 곳

| 메시지·상황 | 이유 | 할 일 |
|---|---|---|
| 트래커 설정이 없다 (`PROVIDER_NOT_READY`) | 트래커 설정 전 | 1절 트래커 설정 |
| 판정 불가 — 수정 범위가 `layerMap` 밖 | 그 경로의 소유자가 스팩에 없다 | 스팩(`solution-design`)에 레이어를 더해 재확정 — **전용 PR 하나로** |
| 남이 배정돼 있다 | 배정 먼저 원칙 | 배정자와 조율 |
| `plan-behind-remote` | 받지 않은 계획 개정이 원격에 있다 | pull 후 다시 |
| STALE — 집은 뒤 티켓 원문이 바뀌었다 | 기준이 바뀌었다 | 다시 `pickup`(재판정·확인) |
| `pr-title-key-required` | PR 제목·브랜치에 티켓 키가 없다 | 제목을 `[AOA-65] …`로, 또는 브랜치에 키 |
| 쓰기 차단(소유권 훅) | 범위·레이어 밖 쓰기 | 범위 안에서 고치거나 판정을 다시 받는다 |
| 릴리스: 보고서 판정이 검증 에이전트 판정과 다르다 | QA 보고서를 옮겨 적으며 판정이 바뀌었거나 검증 없이 썼다 | 해당 검증 에이전트를 다시 돌린다 |

## 8. 하네스가 보장하는 것과 아닌 것

- **보장(코드가 막는다)**: 스팩 없이 개발 에이전트 쓰기 불가 · 레이어·수정 범위 밖 쓰기 차단 · 증거 폴더(receipt·판정 기록)는
  Write/Edit로 고칠 수 없음 · 검증 에이전트 판정과 다른 QA 보고서로 릴리스 불가 · 같은 이름의 프로젝트 에이전트가 하네스 권한을 물려받지 않음.
- **보장하지 않음(사람·모델 몫)**: 판정이 옳은지(근거 문자열까지만 본다) · 리뷰가 실제로 돌았는지 · 완료 조건 문장이
  실제로 충족됐는지(테스트 인용과 범위 변화까지만 본다). 한계 목록은 `docs/protected-core.md` §4.

## 9. 요청 문장 모음

세션을 `/web-harness:wh`로 켠 뒤에는 아래 문장을 **그대로** 말하면 된다(하네스 모드). 켜지 않은 세션이면 문장 앞에 `/web-harness:wh`를 붙인다.

| 하고 싶은 것 | 이렇게 말한다 |
|---|---|
| 하네스 켜기 | `/web-harness:wh` (무엇을 할지 묻는다) |
| 기획 없이 티켓 만들기 | ○○ 작업을 개발 티켓으로 나눠줘 |
| 공통 로직 티켓 | state 공통 로직을 개발 티켓으로 만들어줘. zustand 공통 스토어를 다른 개발자(AI 포함)가 그대로 따라 쓰게 하려는 목적이야. 이미 있는 스토어 코드나 끝난 티켓과 겹치면 새로 만들지 말고 차이만 알려줘. 완료 조건에 lint 강제·사용법 문서·스팩 결정 기록을 넣어줘 |
| 티켓 집기 | AOA-65 픽업 |
| 지금 집을 수 있는 것 | 보드 보여줘 |
| PR 전 리뷰 | AOA-65 PR 연결 미리 보고 리뷰해줘 |
| 연결 | AOA-65를 <PR 주소>에 연결 |
| 티켓 없이 버그 수정 | 설정 화면에서 저장 버튼이 두 번 눌려 (하네스가 fix로 판정 — 새 화면·route면 change로 올린다) |

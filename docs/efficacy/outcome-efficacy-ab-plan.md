# 결과 효능 A/B 실행 계획 (M2 Part 2)

> 사전등록 문서. **실행 전에 고정하고, 실행 후 변경하지 않는다** — 사후에 엔드포인트·분석을
> 고르면 원하는 답이 나온다(I1 위반). 변경이 필요하면 변경 사실과 사유를 append하고 원문은 남긴다.
>
> 상태: **Stage 0 완료 · 라이브 실행은 사용자 토큰 예산 승인 대기**(README §5 게이트 유지).

## 1. 답하려는 질문 (하나만)

**게이트 ON이 OFF보다 스폰 실패율을 낮추는가?**

`README.md` §2의 두 질문 중 **결과 효능**만 다룬다. 탐지 효능은 2026-08-18 측정 완결이며 이
문서는 그것을 재주장하지 않는다.

## 2. ON 베이스라인 실측 (파일럿 2, n=91 스폰)

| 지표 | 정의 | 실측 |
|---|---|---|
| **미완율** | `outcome ∈ {truncated, crashed, incomplete}` | **20.9%** (19/91 — incomplete 10 + truncated 9) |
| runaway율 | `tokens > 120k` **또는** `durationMs > 20min` | 47.3% (43/91 — tokens 단독 42 + duration 단독 추가 1, OR 결합) |
| retry율 | `retry === true` | 37.4% (34/91) |
| 스폰당 토큰 | 계측분 평균 | 163,761 (78/91 계측) |

산출: `node .claude/scripts/report-execution-telemetry.mjs --project <root>` + telemetry 원본.
**OFF 베이스라인은 존재하지 않는다** — 이 문서의 존재 이유다.

## 3. 사전등록 — 엔드포인트와 분석 (실행 전 고정)

- **주 엔드포인트**: 미완율(위 정의). 단일 지표이며 실행 후 교체 금지.
  - 선택 사유: 게이트가 직접 방어하는 실패 형상이고(완결성 게이트), 판정이 이진이며 이미
    telemetry에 기록된다. runaway율은 임계(120k)가 형태 의존이라 2형태 비교에 부적합하고,
    retry율은 오케스트레이터 재량이 섞여 게이트 효과와 교란된다.
- **부 엔드포인트**(보고만, 판정 근거 아님): runaway율, retry율, 완주까지의 총 토큰.
- **분석 단위**: 스폰. **run(앱 1개 빌드)을 클러스터로 하는 클러스터-로버스트 비율 비교**를
  쓴다 — 같은 run 안의 스폰은 독립이 아니다(같은 스펙·같은 세션).
- **보고 형식**: 효과 크기(위험차 pp)와 **신뢰구간**. p-value 단독 보고 금지.
- **분석 코드는 데이터 수집 전에 작성**하고 커밋한다(`analyze-ab.mjs`). 수집 후 작성 금지.

## 4. 검정력 — 정직한 한계

클러스터 설계라 유효 표본이 크게 줄어든다. run당 ~90스폰, ICC를 보수적으로 0.05만 잡아도
설계 효과 = 1 + (90−1)×0.05 ≈ **5.5배**. 즉 run 3개(270스폰)의 유효 표본은 ~49다.

베이스라인 20.9%에서 **대형 효과**(예: OFF 40%, +19pp)를 80% 검정력으로 잡으려면 arm당 유효
표본 ~80 → **arm당 run 4~5개**가 필요하다. 형태 1개·arm 2개만 해도 8~10 run × 2.8M =
**22~28M 토큰**으로, README가 적은 10~20M을 이미 넘는다.

**결론: 명시된 예산으로는 run 수준 유의성 검정이 불가능하다.** 그래서 아래 단계 설계는
"유의성"이 아니라 **방향성과 효과 크기 추정**을 목표로 하고, 그 한계를 라벨에 박는다.

## 5. 단계 설계 (각 단계가 독립적으로 가치를 냄)

### Stage 0 — 도구 (라이브 0 토큰, 결정론)

1. **암 토글**: 스크립트 플래그가 아니라 **실행 지시 변형**이다(게이트 bypass env는 하드 정책이
   막는다 — `global-bash-policy-lib.mjs`). 주입 지점 `run-eval-executor.mjs:97`
   (`const prompt = \`${scenario.entrySkill} ${scenario.prompt}\``)에 env-gated 지시를 덧붙인다:
   OFF 암은 "fit-gate·완결성 게이트·resume-manifest를 호출하지 말 것"을 명시.
2. **암 태깅**: telemetry `run` 라벨에 `+gatesOff` 접미(기존 라벨이 이미 mode를 인코딩:
   `fresh|iterate|resume`). 리포터가 암별 집계를 내도록 확장.
3. **분석 스크립트**: `docs/efficacy/analyze-ab.mjs` — 암별 미완율 + 클러스터-로버스트 CI.
   **Stage 1 실행 전에 커밋**한다.
4. 각 도구에 회귀 테스트(합성 telemetry 입력 → 기대 집계).

**게이트**: Stage 0이 끝나기 전에는 라이브 토큰을 1도 쓰지 않는다.

### Stage 1 — OFF 단일 파일럿 (~2.8M, 승인 필요)

형태 1개(저비용 쪽)에서 **OFF 1 run**만 실행한다. 목적은 검정이 아니라:

- **사상 최초의 OFF telemetry 확보**(현재 0건 — 이게 가장 큰 공백)
- 토글이 실제로 작동하는지 확인(OFF 암에서 게이트 호출이 정말 0인지 트레이스로 검증)
- 효과 크기의 1차 추정 — ON 20.9% 대비 OFF가 어디쯤인지

**Stage 1 receipt 필수 항목**(적대 검토 MEDIUM 반영, 2026-08-20): 아래를 모두 기록하지 않으면
그 run은 A/B 데이터로 쓰지 않는다.
- `checkArmCompliance('off', executor.log)` 출력 — 3게이트 호출 흔적 수. **0이 아니면 폐기**(§6).
- telemetry `run` 라벨의 `+gatesOff` 실제 부착 여부(자기보고이므로 라벨 유무를 눈으로 확인).
- 하니스 커밋 SHA·모델·시나리오 id.
- 이 self-attestation 의존은 `docs/protected-core.md` §4 "A/B 암 토글" 행에 등록돼 있다.

**운영 제약**: `--arm`은 `global-bash-policy-lib.mjs`의 `evalExecutorContract`가 서브에이전트·
샌드박스 Bash 경로에서 차단한다(`--scenario <id> [--dry-run]`만 허용). 따라서 **Stage 1은 사람이
메인 세션에서 직접 실행**해야 하며 서브에이전트에 위임할 수 없다.

**중단 규칙**: OFF run이 예산 1.5배(4.2M)를 넘거나 앱이 완성 불가 상태로 붕괴하면 즉시 중단하고
그 사실 자체를 결과로 기록한다("OFF는 완주 불가"도 유효한 발견이다).

**Stage 1 이후 분기**(사전 고정):
- 차이가 **크고 명백**(예: OFF 미완율 ≥ 40% = 2배 이상) → 방향성 결론을 **"n=1 관찰"**로 정직
  라벨링해 보고하고, Stage 2는 예산 재승인 시에만.
- 차이가 **작거나 모호**(±10pp 이내) → Stage 2 없이는 결론 불가임을 명시하고 중단. 작은 차이를
  n=1로 주장하지 않는다.

### Stage 2 — 매트릭스 (조건부, 22~28M, 별도 승인)

2형태 × 2암 × replicate 4~5. Stage 1에서 효과가 실재하나 크기가 모호할 때만 착수한다.
형태 = local-domain-state(seminar류) + enterprise-search(`ai-scenarios.json` 5종 보유).

## 6. 교란 통제

- **순서 효과**: 암을 번갈아 실행(ON→OFF→ON…). 모델·하니스 버전이 중간에 바뀌면 그 run은 폐기.
- **하니스 버전 고정**: 모든 run을 같은 커밋에서 실행하고 SHA를 receipt에 박는다.
- **오케스트레이터 오염**: OFF 암에서 게이트를 "습관적으로" 호출하면 암 구분이 무너진다 —
  트레이스에서 게이트 스크립트 호출 수를 세어 OFF run이 0인지 검증하고, 0이 아니면 그 run을 폐기.
- **동일 시나리오**: 암 간 프롬프트·시나리오를 동일하게 유지(토글 지시문만 차이).

## 7. 무엇을 주장할 수 있고 없나

| 결과 | 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|---|
| Stage 1만 완료 | "OFF 1회 관찰에서 미완율이 X%였다" | "게이트가 효과 있다"(n=1) |
| Stage 2 완료 | "형태 2개에서 효과 크기 Xpp (CI …)" | 일반 모집단 인과("이 하니스·이 모델·이 시나리오에서") |
| 어느 단계든 | 관측된 수치 | 결함률·품질 개선(측정 대상이 스폰 실패율이지 결함률이 아니다) |

**특히**: 이 A/B는 "게이트가 앱 품질을 높이는가"를 측정하지 **않는다**. 스폰 실패율만 본다.
품질 효능은 별도 질문이며 이 문서 범위 밖이다.

## 10. 사전등록 변경 #1 (2026-08-25, **데이터 수집 전** 기록)

**변경**: Stage 1을 "OFF 1 run"에서 **"같은 커밋·같은 모델·같은 시나리오에서 ON 1 run + OFF
1 run(페어)"**로 바꾼다. 비용 ~2.8M → ~5.6M.

**사유**: 원안은 OFF 신규 run을 §2의 ON 베이스라인(파일럿 2, 20.9%)과 비교하도록 되어 있었다.
그러나 그 베이스라인은 **다른 커밋·다른 모델**에서 나온 값이고, 같은 문서 §6이 교란 통제로
"모든 run을 같은 커밋에서 실행하고 SHA를 receipt에 박는다"를 이미 요구한다. 또 §9는 파일럿 2의
91스폰을 "참조값이지 A/B의 ON 암이 아니다"라고 스스로 규정한다. 원안대로면 관측된 차이가
**암 효과 + 하네스 버전 + 모델 변화**의 합이 되어 어느 쪽에도 귀속할 수 없다 — 즉 원안 Stage 1은
설계상 §6·§9와 모순이었다.

**변경하지 않는 것**: 주 엔드포인트(미완율), 분석 단위(스폰, run 클러스터), 보고 형식(효과 크기
+ CI), 분석 코드(`analyze-ab.mjs`, 이미 커밋됨), 중단 규칙, §7 주장 한계. 페어여도 **n=1 대 n=1**
이므로 §7의 "Stage 1만 완료" 행이 그대로 적용된다 — 유의성은 주장하지 않는다.

**실행 파라미터 (사전 고정)**
- 시나리오: `local-domain-state-workflow` (`.claude/evals/scenarios.json`, entry `/web-orchestrator`)
- 하네스 SHA: **이 변경을 커밋한 직후의 HEAD로 고정**하고 receipt에 실측 기록한다. 실제 제약은
  "두 run 사이에 하네스 커밋 금지"이며, 사이에 커밋이 끼면 두 run 모두 폐기
- 순서: ON → OFF (§6 순서 효과 — 순차 실행. 병렬 금지: runaway 판정에 durationMs 20분 임계가
  있어 동시 실행은 duration을 오염시킨다)
- 중단 규칙: run당 4.2M 초과 또는 붕괴 시 중단, 그 사실을 결과로 기록
- 폐기 규칙: OFF run의 `checkArmCompliance('off', executor.log)`가 0이 아니면 폐기

**원문은 §1~§9 그대로 남는다.** 이 절은 append이며 위쪽 어떤 문장도 수정하지 않았다.

## 11. 사전등록 변경 #2 (2026-08-26, **유효 데이터 수집 전** 기록)

**변경**: executor 프롬프트에 **비대화 실행 규약**을 추가한다 — 암과 무관하게 ON/OFF 양쪽에
동일 문자열로 적용된다(`run-eval-executor.mjs`의 `nonInteractiveInstruction`).

**사유 (실측 근거)**: 변경 #1에 따라 SHA `e482dd8`에서 ON run을 실행한 결과, executor가
**스폰 0개·exit 0**으로 3분 만에 종료했다. `eval-runs/_aborted/`의 executor.log 실측:
모드 감지 배너 출력 → intake 3문 제시 → `추천안으로 진행합니다.` → **턴 종료**.

원인은 구조적이다. executor는 `claude -p "<스킬> <프롬프트>"` **단일 비대화 턴**으로 하네스를
구동하는데, web-orchestrator의 상호작용 계약(`references/interaction-contract.md`,
`approval-checkpoints.md`)은 intake 질문과 Phase 체크포인트에서 **사람의 답을 기다리도록**
설계돼 있다. `-p`에는 답할 사람이 없다.

이것이 주 엔드포인트를 무효화한다: 세션 종료로 폐기된 선행 run은 같은 명령으로 스폰 2개까지
진행했다 — 즉 **모델이 한 턴 안에서 self-continue하는지가 비결정적**이고, 미완율이 그 변동에
지배돼 게이트 ON/OFF 효과는 노이즈에 묻힌다. 양쪽 암이 같은 이유로 실패한다.

**교란이 아닌 근거**: 이 지시는 상호작용 계약(질문/승인 대기)만 건드리며, 이 실험의 측정
대상인 runaway 방어 3게이트(fit-gate·완결성 게이트·resume-manifest)는 건드리지 않는다.
ON/OFF에 **동일 문자열**로 붙으므로 암 간 차이에 기여하지 않는다(§6 "동일 시나리오" 유지).

**변경하지 않는 것**: 주 엔드포인트(미완율), 분석 단위, 분석 코드, 중단 규칙, §7 주장 한계,
변경 #1의 ON/OFF 페어 설계.

**폐기된 run (분석 입력 사용 금지, `eval-runs/_aborted/`에 격리·사유 기록)**
- `ON-2026-08-25T15-04-48-904Z-session-teardown` — 세션 종료로 외부 중단(스폰 2). 암 태깅
  라이브 실증(`+gatesOn` 라벨 실측)이라는 부산물은 남는다.
- SHA `e482dd8`의 ON/OFF 페어 — intake 정지로 무효(위 사유).

**부수 발견 (A/B와 무관, 별도 처리 대상)**: executor stderr에
`Permission deny rule (.claude/settings.json): Write(.claude/**) is not matched by file
permission checks — only Edit(path) rules are.` — `.claude/**` 쓰기 deny 규칙이 실제로는
아무것도 막지 않는다.

**원문 §1~§10은 그대로 남는다.** 이 절은 append이며 위쪽 어떤 문장도 수정하지 않았다.

### 11-1. 변경 #2가 만드는 외적 타당성 한계 (정직 표기)

비대화 규약은 intake 질문뿐 아니라 **Phase 체크포인트·설계 승인 대기도 함께 끈다**. 즉 이
A/B가 재는 것은 "사람 체크포인트 없이 자율 실행되는 하네스"이지, 사람이 승인하며 쓰는 평소의
하네스가 아니다. 파일럿 실측(그린필드 파일럿 1·2)에서 자동 빌더는 오케스트레이터 개입 없이는
runaway·절단됐으므로, 이 조건은 **양쪽 암 모두에 불리한 방향**으로 작용할 가능성이 높다.

양쪽 암에 동일 적용이라 암 간 비교는 유지되지만, 결과를 "평소 사용 조건에서의 게이트 효능"으로
일반화할 수 없다. §7 주장 한계표에 다음 줄을 더한다:

| 결과 | 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|---|
| 변경 #2 적용 run | "사람 체크포인트 없는 자율 실행에서 관측된 값" | 사람이 승인하며 쓰는 평소 조건의 효능 |

### 11-2. 엔드포인트 fail-closed 수정 (변경 #2에 포함)

실측 계기: 위 OFF run의 스폰 3개가 전부 `outcome: undefined`였다. 그런데 `analyze-ab.mjs`
초판은 분모에 전 스폰을 넣고 분자만 `INCOMPLETE`로 세어, **미상을 조용히 완주로 집계**했다.
그 상태로 이 페어를 분석하면 "OFF 미완율 0%" — 게이트를 끈 쪽이 완벽했다는 결론이 나온다.

또한 `outcome`은 측정 대상인 오케스트레이터의 **자기보고**다. 게이트 효능을, 게이트가 붙은
에이전트가 자기 자신에 대해 쓴 값으로 재는 구조였다(I2 위반).

수정(데이터 수집 전 고정):
- `classifyOutcome()` 3분류 — 미상(미기록·비문자열·빈 문자열)은 완주가 아니다
- 미상은 분자·분모 양쪽에서 제외하고 그 수를 항상 보고
- 한 run의 미상 비율이 `UNKNOWN_RATIO_INVALID`(20%)를 넘으면 그 run을 **무효 표시**하고
  판정을 `DATA_INVALID`로 바꾼다 — 수치를 해석하지 말라고 못박는다
- 회귀 반증 테스트 포함: fail-open 동작이 되살아나면 실패하는 테스트(16/16 통과)

**남는 한계(§4 등록 대상)**: 이 수정은 미상을 성공으로 세는 것을 막을 뿐, `outcome`이
자기보고라는 사실 자체는 해소하지 않는다. 실해소는 telemetry가 아니라 executor.log·산출물
실존에서 outcome을 도출하는 것이다 — grader가 이미 그 방식으로 작동한다.

## 12. 사전등록 변경 #3 (2026-08-26, **유효 데이터 0건 상태에서** 기록)

**변경**: 주 엔드포인트를 **미완율 → runaway율**로 교체한다. 미완율은 부 엔드포인트(기술 통계
전용)로 강등하고 **암 간 비교에 쓰지 않는다**.

- runaway율 = `tokens > 120,000` **또는** `durationMs > 20분`인 스폰의 비율
- 이 정의는 §2에서 ON 참조값(47.3%)을 산출할 때 이미 고정된 것이며 데이터를 보고 고르지 않았다

**사유 — 원 설계는 논리적으로 성립하지 않았다.** `execution-budget-contract.md`가 명시한다:

> `outcome`은 "스폰 완결성 게이트" 판정 결과다 … 게이트를 돌리지 않았으면 `outcome`을 생략한다

OFF 암이 끄는 runaway 방어 3게이트 중 하나가 **바로 그 완결성 게이트**다. 따라서 지시를
준수한 OFF run은 outcome이 전량 비는 것이 계약상 정상이고, 미완율은 OFF 암에서 **정의상 측정
불가**다. 온도계가 도움이 되는지 알아보겠다고 온도계를 뺀 뒤 그 온도계로 온도를 읽는 구조였다.

변경 #2의 fail-closed 수정을 적용하면 준수 OFF run은 미상 100% → 자동 `DATA_INVALID`가 되어,
**Stage 1을 그대로 돌리면 ~5.6M을 쓰고 OFF 암이 해석 불가인 것이 보장**된다. 적대 리뷰
(harness-change-reviewer, 2026-08-26)가 이 구조를 지적했다.

**왜 runaway율인가**
1. **암 독립** — `tokens`·`durationMs`는 게이트 호출 여부와 무관하게 기록된다. 실측 반증:
   폐기된 OFF run(스폰 6, outcome 전량 미상)에서 주 엔드포인트는 6/6 측정됐고 부 엔드포인트는
   `DATA_INVALID`였다.
2. **개입과 정합** — 이 실험이 끄고 켜는 것이 문자 그대로 "runaway 방어 3게이트"다. 게이트가
   방어한다고 주장하는 실패 형상을 직접 잰다.
3. **사후 선택이 아님** — §3에 부 엔드포인트로 이미 정의·고정돼 있었고 §2에 ON 참조값도 공표돼
   있다. §3이 주 엔드포인트에서 뺀 사유는 "임계가 형태 의존이라 **2형태 비교**에 부적합"인데,
   Stage 1은 단일 형태 within-form 비교라 그 사유가 적용되지 않는다.

**p-hacking이 아닌 근거**: 이 시점의 유효 데이터는 **0건**이다. 실행된 run 3개는 전부 폐기됐고
폐기 사유가 모두 결과-독립적이다(외부 세션 중단 / intake 정지로 스폰 0 / 짝 파괴). 엔드포인트
값을 보고 고른 것이 아니라, 한쪽 암에서 **측정 자체가 불가능함**을 발견해 교체했다. 데이터가
한 건이라도 유효해진 뒤에는 이 교체가 불가능하다 — 그래서 지금 고정한다.

**변경하지 않는 것**: 분석 단위(스폰, run 클러스터), 클러스터-로버스트 CI, 보고 형식(효과 크기
+ CI, p-value 단독 금지), 중단 규칙, §7 주장 한계표, 변경 #1의 ON/OFF 페어 설계, 변경 #2의
비대화 규약과 미상 fail-closed.

**미상 fail-closed는 새 엔드포인트에도 동일 적용**: `tokens`·`durationMs`가 **둘 다** 없으면
미상이며 정상으로 세지 않는다(회귀 테스트 고정). `tokens: null`은 계약상 허용되므로 duration
단독 판정이 성립한다.

**남는 한계(정직 표기)**: runaway 임계(120k / 20분)는 형태 의존 값이다. Stage 2에서 형태를
추가하면 형태별로 임계를 재고정해야 하며, 형태 간 절대값 비교는 하지 않는다.

**원문 §1~§11은 그대로 남는다.** 이 절은 append이며 위쪽 어떤 문장도 수정하지 않았다.

# 결과 효능 A/B 실행 계획 (M2 Part 2)

> 사전등록 문서. **실행 전에 고정하고, 실행 후 변경하지 않는다** — 사후에 엔드포인트·분석을
> 고르면 원하는 답이 나온다(I1 위반). 변경이 필요하면 변경 사실과 사유를 append하고 원문은 남긴다.
>
> 상태: **Stage 0 완료 · 라이브 실행은 사용자 토큰 예산 승인 대기**(README §5 게이트 유지).

## 1. 답하려는 질문 (하나만)

**게이트 ON이 OFF보다 스폰 실패율을 낮추는가?**

`README.md` §2의 두 질문 중 **결과 효능**만 다룬다. 탐지 효능은 2026-08-18 측정 완결이며 이
문서는 그것을 재주장하지 않는다.

## 2. ON 베이스라인 실측 (파일럿 2, n=91 스폰)

| 지표 | 정의 | 실측 |
|---|---|---|
| **미완율** | `outcome ∈ {truncated, crashed, incomplete}` | **20.9%** (19/91 — incomplete 10 + truncated 9) |
| runaway율 | `tokens > 120k` **또는** `durationMs > 20min` | 47.3% (43/91 — tokens 단독 42 + duration 단독 추가 1, OR 결합) |
| retry율 | `retry === true` | 37.4% (34/91) |
| 스폰당 토큰 | 계측분 평균 | 163,761 (78/91 계측) |

산출: `node .claude/scripts/report-execution-telemetry.mjs --project <root>` + telemetry 원본.
**OFF 베이스라인은 존재하지 않는다** — 이 문서의 존재 이유다.

## 3. 사전등록 — 엔드포인트와 분석 (실행 전 고정)

- **주 엔드포인트**: 미완율(위 정의). 단일 지표이며 실행 후 교체 금지.
  - 선택 사유: 게이트가 직접 방어하는 실패 형상이고(완결성 게이트), 판정이 이진이며 이미
    telemetry에 기록된다. runaway율은 임계(120k)가 형태 의존이라 2형태 비교에 부적합하고,
    retry율은 오케스트레이터 재량이 섞여 게이트 효과와 교란된다.
- **부 엔드포인트**(보고만, 판정 근거 아님): runaway율, retry율, 완주까지의 총 토큰.
- **분석 단위**: 스폰. **run(앱 1개 빌드)을 클러스터로 하는 클러스터-로버스트 비율 비교**를
  쓴다 — 같은 run 안의 스폰은 독립이 아니다(같은 스펙·같은 세션).
- **보고 형식**: 효과 크기(위험차 pp)와 **신뢰구간**. p-value 단독 보고 금지.
- **분석 코드는 데이터 수집 전에 작성**하고 커밋한다(`analyze-ab.mjs`). 수집 후 작성 금지.

## 4. 검정력 — 정직한 한계

클러스터 설계라 유효 표본이 크게 줄어든다. run당 ~90스폰, ICC를 보수적으로 0.05만 잡아도
설계 효과 = 1 + (90−1)×0.05 ≈ **5.5배**. 즉 run 3개(270스폰)의 유효 표본은 ~49다.

베이스라인 20.9%에서 **대형 효과**(예: OFF 40%, +19pp)를 80% 검정력으로 잡으려면 arm당 유효
표본 ~80 → **arm당 run 4~5개**가 필요하다. 형태 1개·arm 2개만 해도 8~10 run × 2.8M =
**22~28M 토큰**으로, README가 적은 10~20M을 이미 넘는다.

**결론: 명시된 예산으로는 run 수준 유의성 검정이 불가능하다.** 그래서 아래 단계 설계는
"유의성"이 아니라 **방향성과 효과 크기 추정**을 목표로 하고, 그 한계를 라벨에 박는다.

## 5. 단계 설계 (각 단계가 독립적으로 가치를 냄)

### Stage 0 — 도구 (라이브 0 토큰, 결정론)

1. **암 토글**: 스크립트 플래그가 아니라 **실행 지시 변형**이다(게이트 bypass env는 하드 정책이
   막는다 — `global-bash-policy-lib.mjs`). 주입 지점 `run-eval-executor.mjs:97`
   (`const prompt = \`${scenario.entrySkill} ${scenario.prompt}\``)에 env-gated 지시를 덧붙인다:
   OFF 암은 "fit-gate·완결성 게이트·resume-manifest를 호출하지 말 것"을 명시.
2. **암 태깅**: telemetry `run` 라벨에 `+gatesOff` 접미(기존 라벨이 이미 mode를 인코딩:
   `fresh|iterate|resume`). 리포터가 암별 집계를 내도록 확장.
3. **분석 스크립트**: `docs/efficacy/analyze-ab.mjs` — 암별 미완율 + 클러스터-로버스트 CI.
   **Stage 1 실행 전에 커밋**한다.
4. 각 도구에 회귀 테스트(합성 telemetry 입력 → 기대 집계).

**게이트**: Stage 0이 끝나기 전에는 라이브 토큰을 1도 쓰지 않는다.

### Stage 1 — OFF 단일 파일럿 (~2.8M, 승인 필요)

형태 1개(저비용 쪽)에서 **OFF 1 run**만 실행한다. 목적은 검정이 아니라:

- **사상 최초의 OFF telemetry 확보**(현재 0건 — 이게 가장 큰 공백)
- 토글이 실제로 작동하는지 확인(OFF 암에서 게이트 호출이 정말 0인지 트레이스로 검증)
- 효과 크기의 1차 추정 — ON 20.9% 대비 OFF가 어디쯤인지

**Stage 1 receipt 필수 항목**(적대 검토 MEDIUM 반영, 2026-08-20): 아래를 모두 기록하지 않으면
그 run은 A/B 데이터로 쓰지 않는다.
- `checkArmCompliance('off', executor.log)` 출력 — 3게이트 호출 흔적 수. **0이 아니면 폐기**(§6).
- telemetry `run` 라벨의 `+gatesOff` 실제 부착 여부(자기보고이므로 라벨 유무를 눈으로 확인).
- 하니스 커밋 SHA·모델·시나리오 id.
- 이 self-attestation 의존은 `docs/protected-core.md` §4 "A/B 암 토글" 행에 등록돼 있다.

**운영 제약**: `--arm`은 `global-bash-policy-lib.mjs`의 `evalExecutorContract`가 서브에이전트·
샌드박스 Bash 경로에서 차단한다(`--scenario <id> [--dry-run]`만 허용). 따라서 **Stage 1은 사람이
메인 세션에서 직접 실행**해야 하며 서브에이전트에 위임할 수 없다.

**중단 규칙**: OFF run이 예산 1.5배(4.2M)를 넘거나 앱이 완성 불가 상태로 붕괴하면 즉시 중단하고
그 사실 자체를 결과로 기록한다("OFF는 완주 불가"도 유효한 발견이다).

**Stage 1 이후 분기**(사전 고정):
- 차이가 **크고 명백**(예: OFF 미완율 ≥ 40% = 2배 이상) → 방향성 결론을 **"n=1 관찰"**로 정직
  라벨링해 보고하고, Stage 2는 예산 재승인 시에만.
- 차이가 **작거나 모호**(±10pp 이내) → Stage 2 없이는 결론 불가임을 명시하고 중단. 작은 차이를
  n=1로 주장하지 않는다.

### Stage 2 — 매트릭스 (조건부, 22~28M, 별도 승인)

2형태 × 2암 × replicate 4~5. Stage 1에서 효과가 실재하나 크기가 모호할 때만 착수한다.
형태 = local-domain-state(seminar류) + enterprise-search(`ai-scenarios.json` 5종 보유).

## 6. 교란 통제

- **순서 효과**: 암을 번갈아 실행(ON→OFF→ON…). 모델·하니스 버전이 중간에 바뀌면 그 run은 폐기.
- **하니스 버전 고정**: 모든 run을 같은 커밋에서 실행하고 SHA를 receipt에 박는다.
- **오케스트레이터 오염**: OFF 암에서 게이트를 "습관적으로" 호출하면 암 구분이 무너진다 —
  트레이스에서 게이트 스크립트 호출 수를 세어 OFF run이 0인지 검증하고, 0이 아니면 그 run을 폐기.
- **동일 시나리오**: 암 간 프롬프트·시나리오를 동일하게 유지(토글 지시문만 차이).

## 7. 무엇을 주장할 수 있고 없나

| 결과 | 말할 수 있는 것 | 말할 수 없는 것 |
|---|---|---|
| Stage 1만 완료 | "OFF 1회 관찰에서 미완율이 X%였다" | "게이트가 효과 있다"(n=1) |
| Stage 2 완료 | "형태 2개에서 효과 크기 Xpp (CI …)" | 일반 모집단 인과("이 하니스·이 모델·이 시나리오에서") |
| 어느 단계든 | 관측된 수치 | 결함률·품질 개선(측정 대상이 스폰 실패율이지 결함률이 아니다) |

**특히**: 이 A/B는 "게이트가 앱 품질을 높이는가"를 측정하지 **않는다**. 스폰 실패율만 본다.
품질 효능은 별도 질문이며 이 문서 범위 밖이다.

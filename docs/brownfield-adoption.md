# 브라운필드 도입 전략 — 도입 사다리 (2026-08-10 결정)

이미 디자인·개발이 완료됐거나 진행 중인 서비스에 web-harness를 도입하는 방법의 정본.
2026-08 analytics-spa 파일럿 연작(델타 프리뷰, 손 재현 프리뷰 불합격, 스냅샷 하이드레이션,
CHG-20260807-001 확정 루프)의 학습을 종합해 프리뷰 중심 접근을 폐기하고 재정의했다.

## 진단 — 왜 프리뷰 중심 접근이 계속 어긋났는가

**greenfield의 정본은 스펙이고, brownfield의 정본은 코드다.** greenfield는 코드가 없으니
스펙→프리뷰→승인→구현이 자연스럽다. brownfield에서 같은 파이프라인을 이식하면 정본이
뒤집힌다 — 손 재현 프리뷰가 실물과 "완전히 다른 디자인"으로 불합격한 것(코드가 정본인데
스펙에서 다시 그림), 스냅샷 방식이 잘 동작한 것(렌더된 코드를 정본으로 인정), 델타가 가장
실물다웠던 것(실행 중 코드가 바탕) 모두 이 비대칭의 증상이다.

따라서 브라운필드 도입은 "greenfield 파이프라인의 이식"이 아니라 **"코드-정본 세계에
harness의 변경 관리 레이어를 얹는 것"**이다.

## 원칙

1. **brownfield의 정본은 코드다.** 스펙·프리뷰는 파생물이며, 브라운필드 스펙의 지위는
   "살아있는 미러"가 아니라 **변경 시점의 확정 기록**(append-only 이력)이다 — 코드가
   나아가며 스펙이 낡는 것은 결함이 아니라 속성이다.
2. **게이트는 harness로 들어온 변경(CR)에만 적용한다.** 팀의 기존 워크플로는 건드리지
   않는다. 도입 범위는 팀이 정한다.
3. **프리뷰는 도구이지 의무가 아니다.** 변경 승인에 시각 확인이 필요할 때만 꺼낸다.
4. **승인 충실.** 프리뷰(델타/스냅샷)로 승인된 기획·디자인은 구현에 **그대로 반영**되어야
   한다. 판정은 주관이 아니라 기계다 — ① 구현 입력은 승인 digest가 가리키는 스펙만
   (프리뷰 코드 이식 금지, Prototype Isolation), ② 완료 판정은 **같은 TC ID의 구현 테스트
   통과** — 콘솔 CR의 구현 검증 레코드(승인된 TC의 부분집합만 기록 가능, 후속 작업 5)가
   그 판정의 기록 표면이다, ③ 신규부 디자인은 기존 디자인 시스템 참조로 기록되므로
   구현이 기존 컴포넌트를 쓰면 시각 충실이 구조적으로 재현된다.

| 레벨 | 이름 | 내용 | 상태 |

**재진입 마커(선택, L0부터 유효)**: 브라운필드 repo는 스캐폴더가 마커를 심을 기회가 없으므로,
루트 `CLAUDE.md`에 `web-harness-managed` 마커 블록(`environment-scaffolder` 재진입 마커 규칙의 블록을 그대로)을
수동으로 append하면 미래 세션이 이 repo를 하네스 관할로 인식하고 재진입 맵(reentry-map.md)의
최소 로드로 진입한다. 플러그인이 설치돼 있으면 SessionStart 훅이 `_workspace/` 감지로 같은
안내를 자동 주입하므로 마커는 훅 미설치 환경의 보완이다.

## 진입점 — 변경 주도 (A안, 확정)

**첫 접점은 "새 변경 요청이 생겼을 때"다.** 등록 의식·init·전면 역추출을 요구하지 않는다
(전면 역추출은 정확도 미검증 + 도입 첫날부터 정본 이원화 drift를 만드는 리스크).

- 콘솔의 빈 프로젝트 화면은 "첫 변경 요청 만들기"를 안내한다(역추출 실행이 아니라).
- 역추출은 항상 **변경에 필요한 인접 표면만** — 낭비와 부패가 없다.
- 선택 옵션 **B-lite**: 원하는 팀은 등록 시 기계 수집 가능한 것만(라우트 목록·화면
  스크린샷/스냅샷) 자동으로 모아 지도를 만들 수 있다. FEAT/TC 같은 의미론은 변경 때 채운다.
- 진행 중 서비스에 기존 PRD/IA 조각이 있으면 `source-artifact-ingestor`로 정규화해 얹는다.

## L1 미니 기획 — 자동 생성 + 사용자 확인 (확정)

형식은 **greenfield feature-plan 형식 그대로** 유지한다(콘솔 파싱·CR 타깃팅·실행기 영향
분석·validator가 무수정으로 동작함이 실증됨). 변경 하나의 산출물:

- `_workspace/01_plan/feature-plan.md` — 기존 기능은 "기존(as-is)" 한 줄씩(인접 표면만),
  신규/변경 기능만 FEAT + `TC-NNN-N: 설명` + 인접 상호작용 목록. 60줄 내외.

**작성 부담은 사람에게 지우지 않는다**: CR 등록(제목·요청·이유·기대 동작) → 에이전트가
CR과 코드에서 미니 기획 초안을 자동 생성 → **사용자 확인 1회** → 이후 영향 분석부터 기존
루프. TC를 파일에 ID로 남기는 이유는 세 가지 연결 때문이다 — Phase 4 테스트 작성 스폰의 동일
TC ID 검증, 콘솔 Features 탭의 추적성 누적(L3 수렴 경로), 이후 변경의 영향 분석 참조.
이것이 harness가 티켓 시스템과 다른 지점이다.

## L1 실행 절차 (runbook — CHG-20260810-001로 실증)

1. **자연어 요청 접수** — 빈 프로젝트도 콘솔에서 시작할 수 있다(2026-08-11 부트스트랩 CR):
   Features 탭의 "첫 변경 요청 만들기"가 대상 FEAT 없는 부트스트랩 CR(Target:
   PROJECT_BOOTSTRAP)을 만든다. 하네스 세션에서 자연어로 시작하는 경로도 그대로 유효하다.
2. **기획 초안 자동 생성** — 두 경로가 있다. ① **콘솔 경로(2026-08-11 개통)**: 대상 없는
   CR의 "기획 정찰"(read-only 역추출 정찰) → "기획 초안 생성"(격리 candidate에 초안) →
   검토·승격이 사용자 확인 1회다. **승인 전 기존 절 보존을 반드시 확인하라** — 파일럿
   실측에서 실행기가 기존 plan을 재작성해 승인된 TC 정의를 파괴한 사례가 있다(지시문에
   보존 조항을 봉합했으나 인간 확인이 최종 방어선). 현재 콘솔 검토 화면은 변경 파일
   목록만 보여주므로 candidate의 plan 파일을 직접 열어 기존 FEAT/TC 절이 남아 있는지
   확인한다(라인 diff 렌더링은 후속 작업 8). ② **하네스 세션 경로**:
   `feature-planner` 에이전트에 요청문 + 프로젝트 루트를 주고 초안을 생성시킨다.
   프롬프트에 반드시 명시할 제약(파일럿에서 실측된 것):
   - TC 라인은 정확히 `- TC-NNN-N: Given..., When..., Then...` — **백틱 금지, ID와 콜론
     사이에 괄호·라벨 금지**(콘솔 파서가 못 읽는다 — 라벨은 콜론 뒤에). 형식 위반은 조용히
     TC 누락으로 나타나므로 생성 후 콘솔 파싱 결과(TC 개수)를 대조한다.
   - Feature List에 기존 기능은 "기존(as-is, 역추출)" 한 줄씩(인접 표면만), 신규만 add.
   - 역추출은 코드 근거(파일 경로)와 함께. 애매한 결정은 발명 금지 — `NEEDS_DECISION`.
   - `## 인접 상호작용` 절 필수. 60줄 내외.
3. **사용자 확인 1회** — 초안 요약 + NEEDS_DECISION을 제시하고 결정을 받아 문서에
   "확정 결정" 절로 기록한다(append-only 이력).
4. **콘솔 CR 등록** — 확정된 FEAT를 대상으로 등록 → 영향 분석 → 격리 candidate(실행기가
   실구현까지 포함할 수 있음 — 파일럿에서 앱 컨벤션·디자인 시스템 준수 확인) → diff 검증
   → 승인 → 정본 승격.
5. **라이브 검증** — 실행 중 dev server(HMR)가 즉시 컴파일하므로, 승격 직후 실제 앱에서
   TC를 실측한다(프리뷰가 없어도 실물 검증이 가능한 이유). 실측 불가한 TC는 사유와 함께
   정직 표기. **자동 실측 채널(2026-08-20)**: 프로젝트 package.json에 TC ID를 위치
   인자로 받는 `test:tc` 스크립트를 선언하면(예: `"test:tc": "vitest run -t"` — 러너
   비의존, 위치 인자 규약만) 콘솔 QA 탭에서 TC별 실행·exit code 기록·재테스트 필요
   표기(소스 스탬프·승인 CR 신호)가 활성화된다. 미선언이면 채널은 fail-closed고 수동
   실측만 남는다. 한계는 protected-core §4 "TC 실행 exit code 판정" 행이 정본.
6. **운영 주의**: 콘솔 CR의 저장 `status`는 검토 결정 전까지 `PROPOSED`로 유지되고 UI의
   IMPACT_REVIEW/READY_FOR_REVIEW는 파생 표시다 — 상태 감시는 `codexRuns`의 run
   status/outcome으로 한다.

## L2 — 태생별 기획 확인 표면 (2026-08-10 재정의)

프리뷰와 라이브 델타는 **별개 항목**이며, 서비스 태생에 따라 하나가 배정된다. 두 표면은
**같은 기획 UX를 공유한다**: 닷+호버 배지 · 기능 사이드바 · 사이드바에서 변경 요청 ·
승인(`UNAPPROVED/APPROVED/STALE` 상태머신). 공유 구현은 공용 오버레이 런타임
(`.claude/skills/web-orchestrator/assets/wh-overlay.mjs`)이다.

| 표면 | 대상 | 특성 | 상태 |
|---|---|---|---|
| 디자인 프리뷰 | greenfield 태생(기획→디자인) | 무의존 프로토타입, 기존 승인 인프라 그대로 | 기존 계약 |
| 라이브 베이스 델타 (`live-base-delta-contract.md`) | brownfield — dev server 위에 신규 기획 델타 적용 | 실물 바탕 + 배지·사이드바·변경요청·승인. digest는 델타 파일+스펙 기준 + 라이브 앵커 검증 receipt(바탕 앱은 digest 밖) | **실증 완료** — FEAT-021 파일럿: validator live-delta 모드 등록 → 라이브 검증(태그·배지·사이드바·TC) → anchorReceipt 승인 → 콘솔 APPROVED 표시. 승인 레코드: `workspace/analytics-spa/_workspace/02_design/design-review.md`(mode live-delta + anchorReceipt JSON) |
| 스냅샷 하이드레이션 | brownfield 폴백 — dev server 실행 불가 시 | 실물 DOM 스냅샷 + 신규부 하이드레이션 | analytics-spa 실증(폴백 강등) |
| 없음 | 문서 diff·스크린샷으로 충분한 변경(L1) | — | 기본값 유지 |

프리뷰든 델타든 **승인된 내용이 실개발의 입력**이다(원칙 4) — 같은 TC ID로 구현이 검증된다.

스냅샷 하이드레이션의 운영 규칙(파일럿에서 확립): 캡처는 스크립트·주입물 제거 + **개인정보
중화**(계정 URL·이름) + **대형 자산 분리**(폰트 등을 별도 파일로 — 에이전트 Read 5MB 제한
때문에 index.html이 영구 수정 불가가 되는 것을 방지). 스냅샷 마크업은 불변, 신규부는
런타임 레이어로만. 델타·스냅샷 모두 **승인용 일회성 증거물**이다 — 유지보수 자산으로
승격하지 않는다.

## 남는 긴장과 방침

- **정본 이원화 drift**: 스펙 = 변경 시점 확정 기록(원칙 1). 다음 변경이 같은 표면을 건드릴
  때 인접 재검증으로 낡음을 그때 해소한다.
- **게이트 vs 도입 마찰**: 게이트는 CR 범위에만(원칙 2). 프리뷰 승인 게이트(APPROVED 없으면
  Phase 3 BLOCKED)는 프리뷰를 만든 경우에만 발동한다 — 프리뷰 없는 L1 변경에 소급 적용하지
  않는다.
- **미검증 영역**: 전면 역추출(B안), 델타는 형태 2개 실증으로 계약 확정(2026-08-10, nocode-live-pilot FEAT-201).
  남은 미검증: 전면 역추출(B안), 스냅샷 하이드레이션의 2번째 형태, Next SSR 스택. 각각
  파일럿 후 계약화한다.

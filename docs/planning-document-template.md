# 기획 문서 템플릿 — 하네스가 읽는 모양

새 기획을 쓰실 때 이 순서로 쓰시면 하네스가 되묻지 않고 바로 진행합니다.
**보통 기획서에 이미 쓰는 것들입니다.** 더해지는 규율은 둘뿐입니다 —
**화면마다 조건을 적는다**와 **기능마다 무엇이 되면 완료인지를 눈에 보이는 것으로 적는다.**

> 이미 PRD·슬라이드 덱이 있으시면 **다시 쓰지 마십시오.** 그대로 주시고 맨 아래
> 「이미 문서가 있는 경우」의 세 가지만 채우시면 됩니다.

## 쓰지 않으셔도 되는 것

- **`PAGE-001` 같은 ID** — 하네스가 붙입니다. 화면 이름만 주십시오.
- **`state:empty` 같은 표기** — 하네스가 변환합니다. 아래 항목 이름 그대로 쓰십시오.
- **Given/When/Then 형식** — 하네스가 test case로 옮깁니다. 평서문으로 쓰십시오.
- **화면 크기·색상값·컴포넌트 이름** — 디자인 단계가 정합니다. 「무엇이 보여야 하는가」까지만.

> 하네스의 내부 표기를 사람에게 요구하지 않는 이유가 있습니다. 계약을 전부 읽고 도는
> 하네스 자신의 정규화 에이전트조차 그 표기를 틀리게 씁니다(실측 2026-09-08).

---

## 0. 이 문서

```markdown
- 판본: v0.1 (2026-09-08)
- 한 줄 요약:
```

판본을 적어 주십시오. 같은 문서의 여러 판본이 섞여 들어오면 하네스가 어느 것이 정본인지
되묻습니다(실측에서 실제로 발생 — 같은 시나리오 ID가 두 판본에 있었습니다).

## 1. 무엇을, 누구를 위해

하네스가 처음 묻는 세 가지입니다. 여기 있으면 묻지 않습니다.

```markdown
- **대상**: 어떤 화면 또는 기능을 만들거나 바꾸는가
- **사용자와 목표**: 누가 그 화면에서 무엇을 끝내려 하는가
- **지금 무엇이 어려운가**:
- **무엇이 관찰되면 성공인가**:
```

마지막 항목이 핵심입니다. **세어지거나 눈에 보이는 것**으로 적어 주십시오.
`사용성이 좋아진다` ✗ / `정원 확인 문의가 절반으로 준다` ✓

## 2. 화면 목록

```markdown
| 화면 | 한 줄 설명 | 순서 |
|---|---|---|
|  |  | 1 |
```

「순서」는 사용자가 탐색하는 정보 구조 순서입니다. 정확하지 않아도 됩니다 — 대략의 순서면
충분하고, 하네스가 이 순서로 안정 ID를 붙입니다.

## 3. 화면별 조건 — 가장 중요

**이 절이 이후 모든 검증의 분모입니다.** 비면 커버리지가 `0/0`으로 서고, 빈 상태·오류·권한 없음
화면을 **구현자가 그 자리에서 정하게 됩니다.**

화면마다 항목 이름은 그대로 두고 내용만 채우십시오.
**해당하지 않는 조건은 비우지 말고 `해당 없음(사유)`로** 적어 주십시오 — 빈 칸은 「이 조건이
없다」가 아니라 「아직 안 정했다」로 읽힙니다.

```markdown
### 화면: <이름>

- **3초 안에 얻어야 하는 것** (1~3개, 중요한 순서대로): ①  ②  ③
- **함께 보이면 좋은 것**:
- **밀도**: 빽빽하게 | 표준 | 여백 있게
- **아직 아무것도 없을 때 보여줄 것**:
- **불러오는 중에 보여줄 것**:
- **불러오지 못했을 때 보여줄 것**:
- **볼 권한이 없는 사람에게 보여줄 것**:
- **일부만 불러왔을 때 보여줄 것**:
- **모바일에서 달라지는 것**:
- **그 밖의 조건**(플랜·역할·상태 등, 있으면):
```

- 「3초 안에 얻어야 하는 것」이 3개를 넘으면 화면을 나누는 것을 검토합니다.
- 상태별 내용은 **컴포넌트 이름이 아니라 사용자에게 보여줄 내용**으로 적어 주십시오.
  `EmptyState 컴포넌트` ✗ / `아직 등록된 항목이 없다는 안내와 첫 등록 버튼` ✓
- 「그 밖의 조건」은 **쓰시는 낱말 그대로** 적으십시오(`무료 플랜`·`관리자`·`승인 대기`).
  하네스가 어휘를 바꾸지 않습니다.

## 4. 기능

기능마다 **무엇이 되면 완료인지**를 눈에 보이는 것으로 적어 주십시오. 이 문장들이 그대로
test case가 되고, 프리뷰·구현·QA가 **같은 기준**으로 움직입니다.

```markdown
### <기능 이름>  — 반드시 | 있으면 좋음 | 이번엔 뺌

- **어느 화면에서**:
- **어떻게 동작하는가** (평서문 2~4줄):
- **무엇이 되면 완료인가**:
  - 정상:
  - 안 되는 경우(권한 없음·조건 미충족·중복):
  - 취소하거나 되돌릴 때:
```

- 「이번엔 뺌」은 **지우지 말고 그대로 두십시오.** 지우면 「작성자가 뺐다」와 「원문에 없었다」를
  구별할 수 없습니다.
- 「무엇이 되면 완료인가」는 **관찰 가능한 결과**로. `잘 동작한다` ✗ /
  `목록에 새 행이 추가되고 상세에도 반영된다` ✓
- 「안 되는 경우」를 빠뜨리기 쉽습니다. 오류·경계는 여기서 안 적으면 아무도 안 적습니다.

## 5. 데이터

```markdown
- **이번 단계에서**: 가짜 데이터로 | 개발 DB 읽기만 | 실데이터 읽기만 | 계약만, 연결은 나중
- **실제 연결로 넘어가는 조건**(위에서 뒤의 셋을 골랐으면):
- **다루면 안 되는 것**(개인정보·로그 금지 항목 등):
```

## 6. 제약 — 아는 것만

```markdown
- 브랜드 제약(색·로고·폰트 지정): 있음/없음, 있으면 어디에
- 다크모드: 필수 | 선택 | 불필요
- 주 사용 기기: 데스크탑 | 모바일 | 둘 다
- 용어·문구 톤: (용어 사전 위치, 존댓말/간결체 등)
- 배포 대상·기술 제약: (있으면)
```

모르는 항목은 **비워 두십시오.** 하네스가 `아직 안 정함`으로 표시하고 시안 승인 때 확정합니다.
지어내서 채우면 그것이 결정으로 굳습니다.

## 7. 디자인 자료 — 있으면

시안이 있으시면 파일과 함께 **어느 화면·어느 조건인지** 한 줄씩 적어 주십시오.
이 표가 있어야 「이 화면의 이 상태는 어느 시안이 근거인가」가 구현까지 이어집니다.

```markdown
| 시안 파일 또는 Figma 프레임 링크 | 어느 화면 | 어느 조건 |
|---|---|---|
|  |  | 기본 |
|  |  | 아직 아무것도 없을 때 |
```

- Figma는 **파일 링크가 아니라 프레임(노드) 링크**를 주십시오.
- **시안이 없는 조건이 있어도 정상입니다.** 비워 두시면 하네스가 「디자인 원리에서 파생」할지
  「다른 조건 것을 재사용」할지를 승인 시점에 묻습니다.

## 8. 분기가 복잡하면 — 다이어그램 대신 문장으로

순서도가 있으시면 그림도 주시되, **연결을 문장으로도** 적어 주십시오. 그림의 화살표는 기계가
읽지 못합니다(실측: PDF 추출에서 분기도의 연결선이 소실돼 `BLOCKER`가 됐습니다).

```markdown
### 분기: <이름>

- 조건: <무엇을 보고 판단하는가>
  - <값 A> → <어느 화면으로 가고 무엇이 보이는가>
  - <값 B> → <어느 화면으로 가고 무엇이 보이는가>
  - 그 밖 / 판단할 수 없을 때 → <무엇이 보이는가>
```

「그 밖 / 판단할 수 없을 때」를 꼭 채워 주십시오. 다이어그램에서 가장 자주 빠지고 구현에서
가장 자주 문제가 되는 자리입니다.

## 채운 예시 — 3절과 4절만

```markdown
### 화면: 신청 목록

- **3초 안에 얻어야 하는 것**: ① 다가오는 일정 ② 정원 대비 신청 수 ③ 마감까지 남은 시간
- **함께 보이면 좋은 것**: 장소, 담당 부서
- **밀도**: 표준
- **아직 아무것도 없을 때**: 예정된 일정이 없다는 안내와 지난 일정 보기 링크
- **불러오는 중에**: 목록 자리를 같은 높이로 잡아두고 자리표시자
- **불러오지 못했을 때**: 마지막으로 본 목록을 그대로 두고 상단에 재시도 배너
- **볼 권한이 없는 사람에게**: 해당 없음(전 임직원이 볼 수 있다)
- **일부만 불러왔을 때**: 받아온 항목만 보이고 하단에 "일부를 불러오지 못했습니다" + 재시도
- **모바일에서**: 카드 1열, 정원은 숫자만
- **그 밖의 조건**: 정원이 찼을 때 — 신청 버튼 대신 「마감」 표시

### 신청하기 — 반드시

- **어느 화면에서**: 신청 목록, 신청 상세
- **어떻게 동작하는가**: 마감 전이고 정원이 남아 있을 때만 신청 버튼이 활성이다.
  누르면 확인 창이 뜨고, 확인하면 신청 수가 즉시 올라가며 버튼이 「신청 취소」로 바뀐다.
  같은 사람이 같은 일정에 두 번 신청할 수 없다.
- **무엇이 되면 완료인가**
  - 정상: 신청 후 목록의 신청 수가 1 늘고 내 신청 내역에 그 일정이 나타난다
  - 안 되는 경우: 마감이 지났으면 버튼이 비활성이고 "신청이 마감되었습니다"가 보인다.
    이미 신청했으면 버튼이 「신청 취소」다
  - 취소할 때: 확인 창에서 취소하면 아무것도 바뀌지 않고 창이 닫힌다
```

## 안 쓰면 어떻게 되는가

빠뜨려도 진행은 됩니다. 다만 **대가가 어디서 나타나는지**가 다릅니다.

| 빠진 것 | 언제 드러나는가 | 무슨 일이 일어나는가 |
|---|---|---|
| 3. 화면별 조건 | 기획 발행 직후 | 조건 분모가 서지 않아 커버리지가 `0/0`. 빈 상태·오류 화면을 **구현자가 정한다** |
| 4. 무엇이 되면 완료인가 | 개발 착수 전 | 「완료」의 기준이 없어 개발이 스스로 판단한다. 팀에 나눠줄 수 없다 |
| 1. 관찰 가능한 성공 조건 | 첫 intake | 하네스가 되묻는다(왕복 1회) |
| 7. 시안 매핑 | 개발 착수 직전 | 어느 시안이 근거인지 남지 않아 시각 검증이 근거 없이 돈다 |
| 8. 분기 문장 | 정규화 시점 | 판정 로직을 복원할 수 없어 `BLOCKER` |
| 0. 판본 | 정규화 시점 | 어느 판본이 정본인지 되묻는다 |
| 4. 「이번엔 뺌」 표시 | 개발 중 | 뺀 기능이 살아 있는 요구로 읽혀 구현된다 |

## 다 못 채워도 됩니다

부분만 주셔도 됩니다. 하네스는 **받은 부분을 정규화하고 빠진 부분만 보강**한 뒤 보강분을
`ASSUMPTION`으로 표시합니다. 그리고 **작성자만이 답할 수 있는 것**은
`_workspace/00_source/author-questions.md`에 **원문의 말로** 되묻습니다 — 하네스 어휘 없이,
어디를 보면 되는지와 답이 없으면 무엇이 막히는지가 함께 적힙니다.

그 질문지에만 답하시면 됩니다.

## 이미 문서가 있는 경우 — 다시 쓰지 마십시오

PRD·슬라이드 덱이 이미 있으면 **그대로** 주십시오. 실측(62쪽 덱 PDF)에서 텍스트로 적힌 것은
거의 다 살아남았고, `BLOCKER` 3건 중 **형식 때문에 난 것은 1건**이었습니다.

PDF가 구조적으로 잃는 것은 둘뿐입니다 — **이미지 전부**와 **다이어그램의 연결선**.
그래서 아래 셋만 따로 주시면 됩니다. 형식은 위 절과 같습니다.

| 따로 주실 것 | 위 어느 절 | 왜 |
|---|---|---|
| 화면별 조건 | 3절 | 대개 표·다이어그램 안에 있어 텍스트로 안 남는다 |
| 시안 매핑 | 7절 | 이미지 레이어가 통째로 소실된다 |
| 분기 로직 | 8절 | 화살표가 이미지라 라벨만 남는다 |

원문의 어느 쪽·어느 절에서 온 것인지 한 줄씩 붙여 주시면 추적이 이어집니다.

# PR Guide Reference

web-harness PR 작성 가이드. `/pr-drafter`에서 초안 작성 시 사용한다.

PR 본문의 목적은 리뷰어가 **어디에 힘을 쓸지** 빨리 정하게 하는 것이다 — 무엇이 바뀌었는지(작업 내용),
동작한다는 근거(증거), 머지하면 무엇이 위험한지(머지 위험).

## PR 템플릿 구조

```markdown
<!-- 사용하고 있는 채널만 사용하면 됩니다 -->
* JIRA: [티켓_번호]()
* Issue: #깃헙_이슈_번호
* 관련 문서(선택): [링크]()

## 작업 내용
1. [변경 사항 요약]
    > 왜 이렇게 해결했는지, 이 방법이 최선인 이유

    [선택: 글보다 빠를 때만 — 호출 트리·diff 스케치·Mermaid 중 하나]

## 증거
- **전:** [실패하던 테스트·출력·스크린샷 — 신규면 `해당 없음(신규)`]
- **후:** [통과한 테스트·출력·스크린샷 — 실행하지 않았으면 `미실행`]

## 머지 위험
**문:** [양방향 | 단방향] — [한 줄 이유]
**영향 범위:** [국소 | 화면 | 기능 영역 | 앱 전체 | 외부 소비자]
[단방향이면: 되돌릴 수 없는 것과 대비책]

## 체크리스트
- [ ] 테스트 통과 (`pnpm test`)
- [ ] 정상 동작 확인
- [ ] 이번 변경으로 어긋난 정본 문서 갱신 (코드 주석의 기본값은 **없음** — `developer.md` 「주석」)

## 기타
[`/team-flow link`가 돌려준 `prBody` 문단이 있으면 여기에 그대로 싣는다]
```

## 작업 내용 작성 원칙

**요약 작성 방법:**
- 1번 항목부터 시작, 변경 사항이 여러 개면 번호를 나눈다
- 요약은 "무엇을 했는지"를 한 줄로 쓴다
- 들여쓰기 블록(`>`)에는 "왜 이렇게 했는지"를 쓴다

**"왜"에 들어가야 하는 내용:**
- 다른 접근 방법이 있었지만 이 방법을 선택한 이유
- 기술적 제약, 성능, 유지보수성 고려 사항
- 관련 이슈나 배경 (알 수 있는 경우)

**좋은 예시:**
```markdown
1. 검색 팝오버를 Popper로 전환해 임베드 위치 문제 해결
    > 기존 absolute 위치 방식은 부모 컨테이너의 overflow:hidden에 의해 잘리는 문제가
    > 있었습니다. Popper를 사용하면 portal로 body에 렌더링되어 클리핑 없이 동작합니다.

2. 사용성 디멘전 그룹 및 스크롤 디멘전 추가
    > 기존 디멘전 목록에서 사용성 관련 항목들이 흩어져 있어 그루핑이 필요했습니다.
    > 스크롤 디멘전은 신규 API 응답 필드를 반영한 것입니다.
```

**글보다 그림이 빠를 때 (선택):** 핵심을 보여 주는 가장 작은 그림 하나를 그 항목 바로 아래에 둔다.
여러 개를 쓰지 않는다. 핵심과 무관한 호출·파일·props는 뺀다.

| 보여 줄 것 | 형태 |
|---|---|
| 로직·분기 | 의사코드 몇 줄 |
| 실행 흐름 | 호출 트리 (들여쓰기) |
| 화면 구조 | 컴포넌트 트리 (상태·모듈 경계 포함) |
| 파일 책임·넓은 리팩터 | 얕은 파일 트리 |
| 이미 있는 모양에서 무엇이 바뀌었나 | 위 형태 중 하나에 `diff` 스케치 (`+`/`-`) |
| 컴포넌트 간 상호작용 | Mermaid `sequenceDiagram` |

```diff
 submitForm
   createSession
     persistPrompt
+    validateQuota
     launchAgent
```

## 증거 작성 원칙

동작한다는 근거를 **전/후**로 보인다. 등급 순서:

1. 스크린샷 — 시각 변경이고 캡처 환경이 있을 때
2. 실행 근거 — 이번 변경 전에 실패하고 후에 통과한 테스트(이름과 단언을 의사코드 한 줄로), 콘솔·CLI 출력
3. 없음 — `미실행`이라고 그대로 적는다

- **실제로 실행한 결과만 인용한다.** 출처는 이번 세션의 실행 출력, CI 결과, `_workspace/04_qa/`의 QA 보고서·영수증이다.
  실행하지 않은 검증을 통과로 쓰지 않는다 — 모르면 `미실행` 또는 `[작성 필요]`다
- 전 상태가 없는 신규 기능은 **전:** `해당 없음(신규)`으로 둔다

## 머지 위험 작성 원칙

**문(door)** — 머지 뒤에 되돌릴 수 있는가. 판별 질문은 하나다: **revert 커밋 하나로 이전 상태가
완전히 돌아오는가?** 그러면 양방향 문, 아니면 단방향 문이다.

단방향 신호 (하나라도 해당하면 단방향):

| 신호 | 예 |
|---|---|
| 데이터를 지우거나 바꾼다 | 컬럼 삭제·변환 마이그레이션, 백필, 저장 데이터 정리 |
| 밖으로 나간 부수효과 | 이메일·푸시·결제·웹훅 발송, 외부 시스템 쓰기 |
| 이미 소비자가 의존하는 공개 계약 | 공개 API·이벤트 스키마·URL·패키지 export 제거·변경 |
| 저장 형식 변경 | DB 스키마, 브라우저 persist 버전, 캐시 키 — 되돌린 코드가 새 데이터를 못 읽는다 |
| 권한·비밀 | 권한 확대, 인증 흐름 변경, 키 노출 |
| 배포 뒤 회수 불가 | 공개된 패키지 버전, 검색 색인(robots·canonical) |

UI·스타일, 공개 계약이 그대로인 내부 리팩터, 플래그 뒤의 기능, 테스트·문서는 보통 양방향이다.

**영향 범위(blast radius)** — 잘못되면 어디까지 번지는가를 한 단어로: `국소`(한 함수·컴포넌트) ·
`화면` · `기능 영역` · `앱 전체` · `외부 소비자`. 필요하면 아래에 예상 증상 한 줄(레이아웃 이동,
모바일 깨짐, 소비자 빌드 실패 등).

- **판단이 서지 않으면 단방향으로 적고 이유를 쓴다.** 낮춰 적는 쪽이 비싸다
- 단방향이면 되돌릴 수 없는 것과 대비책(백업·플래그·단계 배포)을 한두 줄 적는다. 개발 중에
  「멈추고 묻기」(되돌리기 어렵거나 팀 전체 영향)를 거친 기록이 없으면 `[확인 필요]`를 붙인다
- 이 섹션은 리뷰어가 힘을 쓸 곳을 정하는 안내다. `양방향 · 국소`라도 테스트·리뷰·게이트를 면제하지 않는다

## 리뷰어 코멘트 컨벤션

PR 설명 하단에 리뷰어를 위한 안내를 포함한다 (템플릿 `<details>` 부분):

| 머리말 | 의미 | 머지 여부 |
|---|---|---|
| `[의견]` | 더 나은 코드가 있는 경우 제안 | 머지 OK |
| `[질문]` | 설명이 부족한 부분에 대한 설명 요청 | 머지 OK |
| `[확인]` | 동작에 지장은 없지만 수정이 필요한 부분 | 머지 전 확인 필요 |
| `[이슈]` | 문제가 발생할 것으로 예상됨 | 머지 전 반영 필요 |

## Draft PR (기획 핸드오프용)

`/wh plan`으로 기획을 마친 뒤 draft PR을 열 때 추가로 포함:

```markdown
## 기획 메모
- 대상 화면:
- 사용자와 목적:
- Mock vs 실데이터:
- 확인 방법:
- 미결 질문:
```

Draft PR에는 `리뷰제외`, `머지금지` 라벨을 붙인다.

## gh 명령 예시

```bash
# 일반 PR
gh pr create \
  --title "[JIRA-000] 작업 제목" \
  --body "$(cat <<'EOF'
[PR 본문]
EOF
)"

# Draft PR (기획 핸드오프)
gh pr create \
  --title "[JIRA-000] 작업 제목" \
  --draft \
  --label "리뷰제외,머지금지" \
  --body "$(cat <<'EOF'
[PR 본문]
EOF
)"
```

# Planning Facilitation Contract

기획은 구현 용어보다 사용자의 화면·업무·불편을 먼저 고정한다. 이미 제공된 문서, 주석, 기존 source에서 확인할 수 있는 내용은 다시 묻지 않는다.

## 제품 중심 첫 Intake

첫 질문은 한 번에 최대 3개이며 다음 순서에서 아직 모르는 항목만 묻는다.

1. **대상** — 어떤 화면 또는 기능을 바꾸거나 만들 것인가
2. **사용자와 목표** — 누가 그 화면에서 무엇을 끝내려 하는가
3. **현재 문제** — 지금 무엇이 어렵고, 어떤 관찰 가능한 변화가 성공인가

API, branch, 파일, 라이브러리, 배포 방식은 첫 질문에 넣지 않는다. 제품 의도가 잡힌 뒤 구조를 바꾸는 데이터·규모·운영 결정만 `interaction-contract.md` 순서로 확인한다.

## 구조적 해석 우선

“어색하다”, “복잡하다”, “거슬린다”, “부자연스럽다” 같은 표현을 곧바로 문구 수정으로 축소하지 않는다. 아래 원인을 먼저 가설로 기록하고 검증한다.

- mode 또는 책임이 섞여 있는가
- 정보 우선순위와 시각 계층이 불분명한가
- 다음 행동과 affordance가 보이지 않는가
- 상태 변화와 피드백이 불명확한가
- layout shift, 밀도, 용어가 이해를 방해하는가

## 자동 UX Check

다음 중 하나라도 해당하면 `planning-context.md`와 `ux-brief.md`에 간결한 `## UX Check`를 작성한다.

- 표·목록·차트·대시보드·필터처럼 정보 밀도가 높은 화면
- 선택·삭제·일괄 작업·권한·소유권·disabled·부분 실패
- 같은 화면에 여러 주석이나 상충하는 피드백
- prototype 또는 목표 상태가 불명확한 요청

형식:

```markdown
## UX Check
- 첫눈에 알 수 있어야 하는 것:
- 다음 행동이 보이는가:
- 실수하거나 오해할 지점:
- 먼저 정할 방향:
- prototype/Phase 2에서 확인할 것:
```

UX Check는 디자인을 확정하지 않는다. Phase 2에서 검증할 우선순위와 위험을 고정한다.

## 주석·스크린샷 피드백

- 같은 화면의 주석은 가능한 한 한 번에 수집하고 서로의 관계를 함께 해석한다.
- 좌표나 DOM 위치를 요구사항으로 복사하지 않고 `대상 / 사용자 의도 / 기대 행동 / 적용 범위 / 확인 방법`으로 정규화한다.
- 주석이 상충하거나 대상이 불명확하면 임의로 합치지 않고 `NEEDS_DECISION`으로 둔다.
- 스크린샷의 현재 상태와 목표 상태를 구분하고, 이미지에 보이지 않는 동작은 추측하지 않는다.

```markdown
## Annotation Review
| ID | 대상 | 정규화한 의도 | 범위 | 확인 방법 | 상태 |
```

## Current Planning Memo

주요 답변 또는 방향 전환 뒤 `planning-context.md`의 memo를 갱신한다.

- 대상 화면/기능
- 주 사용자와 목적
- 확인된 요구사항
- 빠진 상태·시나리오
- 가정과 검증 방법
- 상대 노력도
- 다음 질문 또는 행동

답변이 바뀌면 이전 결정과 이유를 `decision-log.md`에 남긴다.

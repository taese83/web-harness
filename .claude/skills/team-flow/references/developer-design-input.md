# 개발 설계 입력 템플릿

이 양식은 WORK 분해 전에 개발자가 가진 정보를 전달하기 위한 **선택** 템플릿이다. 기존 문서가 있으면 링크·경로·관련 절만 적고 내용을 다시 쓰지 않아도 된다. 내부 ID·JSON·해시는 harness가 관리한다(`work-plan-contract.md`). 받은 자료는 `00_source/`에 원문으로 보존되며, 자료를 냈다는 이유로 승인된 결정이 되지 않는다.

기획자·개발자가 `/wh plan` 결과를 검토한 뒤 개발 준비 담당자가 `team-flow claim`에 이 자료를 전달한다. claim이 전체 분석·분해안을 제시하고 검토를 받는다(검토한 판본의 발행은 다음 단계에서 같은 claim이 잇는다). 별도 분해 명령이나 완성된 work-plan 입력은 필요 없다.

- 이번 범위에서 제외할 것:

## 상태 처리

| 상태 | 원본/파생 | 소유 위치 | 누가 변경하나 | 갱신·초기화 시점 | 보존·복구 규칙 |
|---|---|---|---|---|---|
| 서버 조회 데이터 | 원본 | 기존 query 계층 | 서버 응답 | 재조회·저장 후 | 기존 정책 참조 |
| 검색 조건 | 원본 | URL 또는 화면 | 사용자 | 검색·초기화 | 뒤로 가기 동작 명시 |
| 편집 draft | 원본 | 폼 내부 | 사용자 입력 | 편집 시작·저장·취소 | 외부 갱신 충돌 정책 명시 |
| 선택 개수 | 파생 | 계산 | 선택 ID에서 계산 | 선택 변경 | 중복 저장하지 않음 |

위 행은 예시다. 실제 설계에 맞게 바꾼다.

- 반드시 유지할 상태 불변식:

- 실패·취소·undo·재시도 처리:
- 새로 고침·탭 이동·영속화·마이그레이션이 필요한 경우:

## 화면과 공통 컴포넌트

- 화면/시안과 조건별 근거:
- 페이지 영역과 조립 위치:
- 기존 UI·token·theme 후보:
- 필요한 props/events/slots·variant:
- loading/empty/error/disabled 상태:
- 접근성·반응형 조건:
- 기존 컴포넌트를 바꿔도 되는 범위:

기존 FEAT·화면·디자인 연결이 있으면 그 문서만 알려줘도 된다. 아래 표는 추가로 설명할 내용이 있을 때 사용하며, 내부 ID나 판본 해시를 직접 작성할 필요는 없다.

| 기능/동작 | 화면·조건 | Figma 프레임/컴포넌트 또는 기존 명세 | 결정 상태·적용 판본(알면) |
|---|---|---|---|
| 회원 정보 수정 | 편집 중·저장 실패 | 해당 프레임 링크 또는 명세 절 | 확정/초안/미정 |

- 해당 부분을 이해하기 위한 전체 사용자 흐름:
- 여러 기능이 함께 참조하는 공통 디자인 근거:
- 시안 없는 조건의 기존 결정(파생/재사용/미정):
- Epic을 사용한다면 첫 연결에서 확인할 동작과 디자인 범위:

Figma를 사용하지 않거나 UI가 없는 작업은 억지로 채우지 않는다. 파일 전체 URL보다 대상 프레임과 어떤 상태인지 알려주는 것이 좋고, 기존 연결에서 알 수 있는 내용은 AI가 승계한다.

## AI에 요청할 내용

```text
/web-harness:team-flow claim
검토한 plan을 기준으로 개발 준비를 시작해줘. 먼저 분해안을 검토할게.
지정한 범위의 FEAT 목록을 먼저 확인하고, 위 자료와 현재 코드를 함께 대조해줘.
현재 구현 설명·목표 설계·참고 대안과 확정·초안 상태를 구분해줘.
관련 공통 모듈과 컴포넌트의 구현·호출부·테스트를 분석하고,
재사용·확장·어댑터·신규·제외·미확인으로 판정해줘.

FEAT 간 공통 요구까지 비교해 공통 기반 WORK와 FEAT별 WORK의 통합 분해안을 만들고,
각 작업의 출처·의존·수정 범위·검증 기준을 연결해줘.
FEAT·TC의 디자인 연결을 유지하고 WORK마다 필요한 화면·조건·컴포넌트와
전체 사용자 흐름을 참조하게 해줘. 기존 연결이 없는 부분은 추측으로 확정하지 마.
Epic을 써도 이 연결은 유지하고, 첫 연결 검증과 전체 완료를 구분해줘.
우선순위는 의존을 지킨 실행 가능 작업 안에서 정하고,
최소 기능을 먼저 연결할 순서와 병행 가능한 범위를 보여줘.
읽지 못한 자료와 미결 사항은 표시하고 임의로 확정하지 마.
아직 티켓 발행이나 제품 코드 구현은 하지 마.
```

## 일반화 근거

- 서버 데이터 중심 화면 — 데이터 흐름·API 명세·폼 draft 소유가 주 입력이다.
- 로컬 문서 상태 중심 편집기 — 공유 상태·명령·불변식·지속성이 주 입력이다.
- 화면 없는 라이브러리·CLI — 화면·Figma 절은 비워 두고 공개 인터페이스·제약만 적는다.

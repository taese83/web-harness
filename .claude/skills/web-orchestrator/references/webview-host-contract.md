# Webview Host Contract

웹앱이 **호스트 앱 안에서 돌 때**(네이티브 웹뷰·인앱 브라우저)의 경계 계약. 호스트는 브라우저가 주지 않는 능력을 주고, 그 대가로 웹앱은 자기 화면 밖의 상태에 의존한다 — 이 계약은 그 의존을 한 곳에 모으고 신뢰 경계를 긋는다.

## 적용

전역 네이티브 인터페이스(`window.<host>.*`, `webkit.messageHandlers.*`), 호스트 전용 스킴 이동, 호스트 앱 버전 분기 중 하나라도 코드에 있으면 이 계약이 선다. **각 에이전트가 코드 신호로 스스로 판정한다** — 오케스트레이터 모드 플래그를 쓰지 않는다(선행 로드 예산 I4).

코드가 아직 없는 그린필드에서는 신호가 없다. 호스트 내장 여부를 기술 선택 단계에서 적고, 그때까지 이 계약은 서지 않는다(`docs/protected-core.md` §4 등록).

## 1. 브리지 파사드

호출부가 호스트 전역을 직접 만지지 않고 한 모듈로 모으는 것은 두 실측 모두 지키고 있다. 계약이 더 요구하는 것은 넷이다.

| 요구 | 왜 |
|---|---|
| **미지원을 타입으로 표현한다** — 호스트가 안 가진 메서드는 옵셔널 | 전역 선언을 non-optional로 두고 런타임에만 가드하면, 타입이 "있다"고 말하는 것을 코드가 매번 부정한다 |
| **호스트가 둘 이상이면 같은 인터페이스의 구현을 갈아 끼운다** | `host = isDesktop ? desktopHost : mobileHost`. 호출부에 호스트 분기를 흘리지 않는다 |
| **양방향으로 정규화한다** | 네이티브는 JSON 문자열·`"true"` 같은 문자열을 돌려주고, 인자도 문자열 JSON이나 base64를 요구하는 경우가 있다. 바깥 형식은 경계에서 끝난다 |
| **호스트 스킴 문자열도 파사드 안이다** | 환경별 스킴 분기(sandbox/prod)가 호출부마다 흩어지면 한 곳을 고쳐도 나머지가 남는다 — 두 실측 모두 3곳 이상에 중복돼 있다 |

호스트 메서드 이름이 버전별로 다를 수 있다(오타 수정·개명). 그 흡수는 파사드의 일이며 호출부로 새지 않는다.

## 2. 능력은 축마다, 기능 단위로

능력 축은 셋이다 — **호스트 앱 버전 · 웹뷰 엔진 버전 · OS 버전**. 하나로 뭉치면 엔진이 낡은 최신 앱을 놓친다.

- **브리지가 존재하는 최소 버전은 전역 하한으로 둔다** — 그 아래에서는 앱이 성립하지 않는다.
- **기능별 최소를 전역 하한으로 끌어올리는 것이 프록시다.** 한 기능 때문에 하한을 올리면 그 기능을 안 쓰는 사용자까지 막힌다. 기능별 게이트는 `canUseX()`로 기능 옆에 둔다.
- **버전 비교는 세그먼트 단위 숫자 비교다.** 문자열·부동소수 비교는 `10.2.0 > 10.10.0`을 만든다.
- 호스트 정보를 읽지 못하면 **없는 것으로 읽는다**(fail-closed).
- 능력이 없을 때의 대체 경로를 함께 정한다 — 안내 화면, 축소된 기능, 외부 브라우저 중 하나. 대체 경로가 없으면 그 기능은 아직 넣지 않는다.

## 3. 액션 위임 경계 (안전 하한)

**서버·모델·호스트가 준 payload가 앱의 이동을 정하면, 그 payload는 신뢰 경계를 넘는 입력이다.**

| 경로 | 규칙 |
|---|---|
| 웹이 직접 이동(`location.assign`·`href`·`window.open`) | **스킴 allowlist 필수.** 허용 스킴을 상수로 선언하고 그 밖은 버린다. `http`/`https` 외를 허용하면 스킴마다 이유를 한 줄 적는다 |
| 호스트에 위임(`host.execute(payload)`) | 호스트가 검증한다는 근거를 **§7의 결박 형식으로** 적는다(출처·확인 시점·적용 버전). 근거 없는 주석은 미이행으로 읽고 웹이 검증한다 |
| 어느 쪽도 아닌 payload | 무시한다(no-op). **매칭 실패를 "일단 열기"로 폴백하지 않는다** — 그 폴백이 allowlist를 무력화한다 |

**웹이 URL을 고르고 호스트는 열기만 하는 경로는 위임이 아니라 직접 이동이다.** 호스트에 넘긴다는 사실이 검증 면제 사유가 되지 않는다.

`code-reviewer` 6(스킴 검사 없는 URL → `location`)이 강제 지점이다. 네이티브 스킴이 필요하다는 것은 예외 사유가 아니라 allowlist에 그 스킴을 올릴 사유다. payload가 LLM 응답에서 오면 `untrusted-content-quarantine.md`가 함께 선다.

## 4. 생명주기와 복귀

- 닫기·복귀·리셋은 파사드 메서드로 둔다. 호스트 메서드가 없으면 공통 스킴으로 폴백하고, 폴백도 없으면 **사용자에게 보이는 실패**로 만든다(조용한 no-op 금지).
- 호스트가 뒤로가기를 가로채면 웹 히스토리와 호스트 스택이 두 개의 진실이 된다. 어느 쪽이 정본인지 선언하고 e2e로 고정한다 — 플랫폼에 따라 히스토리를 아예 쓰지 않는 선택도 유효하다.
- **웹뷰를 재사용하는 호스트에서는 초기화가 다시 일어나지 않는다.** 진입 시 한 번 읽는 값(공유 텍스트·시작 프롬프트)을 초기화 경로에만 두면 두 번째 진입에서 유실된다 — 그 호스트에는 push 채널이 필요하다.
- **요청-응답과 push를 이벤트 이름으로 분리한다.** 같은 이름을 쓰면 push가 대기 중인 resolver를 가로챈다.
- **복귀 파라미터는 1회 소비한다.** 재진입 URL의 결과 파라미터를 읽은 뒤 히스토리를 늘리지 않고 지운다 — 남겨 두면 새로고침·뒤로가기에서 같은 동작이 다시 난다.
- **외부 앱으로 나갔다 오는 흐름은 복귀 시그널을 신뢰하지 않는다.** 인증서·결제처럼 호스트 밖으로 나가는 전이는 복귀 이벤트가 오지 않을 수 있다 — 나가는 즉시 폴링을 시작하고 상한(횟수·시간)을 둔다. 폴링 중 네트워크 오류는 다음 주기로 넘긴다.
- **호스트가 둘이면 복귀 방식도 둘일 수 있다.** 한쪽은 URL 재진입, 다른 쪽은 push 이벤트다. 재진입으로 이미 화면이 갱신된 경로에서 또 이동시키면 직전에 띄운 UI가 사라진다.

## 5. 호스트 설정 동기화

폰트 배율·테마·고대비는 **OS와 호스트 앱 두 층**에서 온다.

- 값은 경계에서 한 번 읽어 앱의 단일 소스(루트 폰트 크기·테마 토큰)에 반영한다. 화면마다 다시 읽지 않는다.
- **범위를 클램프한다.** 접근성 배율은 상한 없이 커져 레이아웃을 깨뜨린다. 플랫폼별 환산이 필요하면 표를 한 파일에 모은다(표의 값은 §7).
- **호스트 크롬을 바꿨으면 되돌린다.** 상태바·세이프에어리어 색을 웹이 바꾸는 호스트에서는 이탈 시점(`pagehide`)에 기본값으로 복구한다 — 안 하면 다음 화면이 남은 색을 물려받는다.
- 호스트가 값을 주지 않으면 브라우저 기본으로 돈다 — 동기화 실패가 화면 실패가 되지 않게 한다.

## 6. 플랫폼 사실

호스트 설정·버전과 무관하게 웹 플랫폼에서 성립하는 것만 둔다. 호스트가 릴리스로 바꿀 수 있는 것은 §7이다.

- **cross-origin iframe 안의 포커스는 감지할 수 없다.** 입력창이 iframe 안에 있으면 키보드 개폐를 직접 알 수 없다 — 뷰포트 높이 변화를 프록시로 쓴다. 키보드가 layout viewport 대신 visual viewport만 줄이는 환경이 있어 `Math.min(innerHeight, visualViewport?.height ?? Infinity)`로 읽는다(후자는 방어적 선택이며 관측이 아니다).
- **측정이 필요한 요소는 언마운트하지 않는다.** 숨길 때 DOM을 제거하면 `scrollHeight` 같은 값을 다시 잴 수 없다 — 클래스로만 숨긴다.
- **모바일 OS가 앱을 백그라운드로 보내면 진행 중인 스트림이 끊긴다.** SSE·롱폴링 에러가 쏟아지므로 `document.visibilityState === 'hidden'`인 스트림 오류는 에러 수집에서 거른다 — 거르지 않으면 진짜 오류가 묻힌다. 어떤 코드가 그 부류인지는 SDK마다 다르다.

**소프트 키보드 리사이즈로 인한 고스트 클릭** — 호스트가 `adjustResize`로 동작하는 Android WebView에서, cross-origin iframe 안의 탭이 리플로우 뒤 부모 문서의 다른 요소에 synthetic click으로 떨어지는 것이 **관측 1건** 있다. 판별은 같은 요소의 `pointerdown` 선행 여부이고, 키보드 접근성 클릭(`event.detail === 0`)은 무조건 통과시킨다. 리사이즈 모드가 호스트 설정이라 이 조건은 §7의 확인 항목이기도 하다.

## 7. 호스트 프로파일 — 값은 프로젝트가 소유한다

§1~6은 규칙이고, **이 호스트의 이 버전이 어떤가**는 계약에 담지 않는다(`docs/rule-tiers.md` 「관측을 얻었을 때」). 판별 질문은 하나다 — **호스트 팀이 릴리스로 바꿀 수 있는가. 그러면 §7이다.**

프로젝트가 자기 산출물로 기록한다(스팩이 정한 위치). 기록할 것:

| 항목 | 예 |
|---|---|
| 파사드 메서드 목록과 호스트별 지원 여부 | 어느 호스트가 무엇을 안 가졌는가 |
| 능력 축 3종의 하한과 기능별 최소 버전 | 호스트 앱 / 웹뷰 엔진 / OS |
| 설정 환산표 | 폰트 배율 단계 ↔ 배수 |
| 허용 스킴 목록과 각각의 이유 | §3 allowlist |
| 검증 주체가 호스트인 경로와 그 근거 | §3 위임 |
| 리사이즈 모드·크롬 제어 등 호스트 동작 | §5·§6 확인 항목 |

각 항목에 **출처·확인 시점·적용 버전 범위**를 적는다(형식은 `docs/audits/receipts/`의 영수증을 따른다). 호스트는 계속 릴리스되므로 결박 없는 값은 다음 판에서 거짓이 된다. 출처는 호스트 팀 문서이거나 실기기 관측이며, **둘 다 없으면 적지 않는다.**

## 8. 호스트 밖 진입

호스트 앱이 아닌 브라우저로 들어오는 사용자가 반드시 생긴다(링크 공유·검색). 브리지 페이지를 하나 두고 **앱으로 보낼지, 축소 기능으로 보여줄지, 안내만 할지**를 선언한다. 선언이 없으면 호스트 전용 코드가 일반 브라우저에서 예외를 던진다.

## 검증

- `security-reviewer`: §3 — allowlist 존재와 적용 지점, 위임 경로의 근거 결박, 매칭 실패 폴백. 누락은 HIGH.
- `code-reviewer`: 파사드 밖 호스트 전역·스킴 접근, 정규화 누락, 폴백 없는 호스트 호출, 기능별 최소를 전역 하한으로 올린 게이트.
- `browser-verifier`: 호스트 없는 환경에서 §8 경로가 서는지. **호스트가 있는 환경은 실기기 확인이며 하네스 범위 밖이다** — UA 위장과 브리지 스텁으로 도는 e2e는 호스트 검증이 아니라는 사실을 보고에 적는다.

## 일반화 근거

- **AI 채팅 웹뷰 A**(단일 라우트, 모바일 호스트 1종): 위젯 액션을 `location.assign`으로 직접 이동하며 allowlist가 없다 — §3의 실재 사례. 전역 인터페이스가 non-optional로 선언돼 있고 런타임은 전부 가드한다 — §1. 폰트 배율은 OS 13단계·앱 8단계 두 축의 환산표를 갖는다 — §5·§7. 한 플랫폼에서 레이어 히스토리를 아예 쓰지 않는다 — §4.
- **AI 셸 웹뷰 B**(다중 라우트, 모바일+데스크톱 호스트 2종): 파사드를 호스트별 구현으로 갈아 끼우고 옵셔널 6개로 미지원을 표현한다 — §1. 데스크톱 호스트는 요청-응답과 push를 분리하고 인증 복귀가 재진입이 아니라 push 이벤트다 — §4. 딥링크 매칭 실패 시 인앱브라우저로 폴백한다 — §3 세 번째 행. 데스크톱 경로는 웹이 URL을 고르고 호스트는 열기만 하므로 위임이 아니다 — §3의 마지막 문장이 여기서 나왔다.
- 두 형태가 §3에서 **반대 선택**을 했고 양쪽 다 검증이 빠진 경로를 가진 것이 이 계약의 계기다.
- 두 형태 모두 **전역 하한과 기능별 게이트를 병행**한다 — §2가 전역 하한 자체를 금지하지 않는 근거다.
- §6은 두 코드베이스의 주석에 남은 관측에서 추렸고 호스트 이름·버전·수치를 담지 않는다. 다른 웹뷰 호스트(Capacitor·RN WebView·타 메신저)에도 서는지는 **미검증**이다.
- 진실 검증 수준: **명명 수준**. 두 코드베이스의 함수 표면과 주석을 대조해 개념을 뽑았고, 이 계약을 적용한 생성·변경 결과는 실측하지 않았다. §6 각 항목의 관측 수는 1~2건이다.

# Requirements — 도서관 열람실 좌석 예약 웹앱

## Product Frame
- 대상 화면/기능: 동네 도서관 열람실 좌석 예약 웹앱 — 오늘 날짜 좌석 현황 조회, 예약, 취소 (모바일 브라우저 우선)
- Primary users: 해당 도서관 정회원(회원번호+비밀번호로 인증되는 기존 회원). 관리자·비회원은 이번 범위 밖.
- Job to be completed: 열람실에 가지 않고 오늘 이용 가능한 좌석을 30분 단위로 찾아 예약하고, 필요하면 취소한다.
- Current pain: 현장에 직접 가야만 빈 좌석 여부를 알 수 있어 헛걸음이 발생한다.
- Observable success criteria: 회원이 (로그인 이후) 좌석 현황 화면 진입 시점부터 예약 확정 피드백을 받는 시점까지 1분 이내에 완료한다. 측정 시작점을 "로그인 완료 후"로 잡은 근거는 아래 Open Decisions의 ASSUMPTION 참고.

## Modes
- LOCAL_DOMAIN_STATE_MODE: false — 좌석·예약은 도서관 REST API가 authoritative store다. 앱은 조회·생성·취소 요청을 API에 그대로 전달할 뿐 브라우저에 도메인 데이터를 영속하지 않는다(로그인 세션 토큰 정도만 예외). 정렬·다중선택·undo·참조관계 같은 로컬 상태 불변식이 없어 `local-domain-state.md` 감지 조건에 해당하지 않는다.
- TIMESERIES_MODE: false — 실시간 메트릭·시계열 차트·모니터링 요구가 없다. 좌석 현황은 "현재 스냅샷 + 필요시 갱신"이며 시계열 집계/backfill이 아니다.
- ANALYTICS_BUILDER_MODE: false — metric/dimension을 조합하는 분석 빌더 요구가 없다.
- EXTERNAL_DATA_INGESTION_MODE: false — 브라우저(또는 앱 서버)가 도서관 API를 매 요청 시 실시간으로 조회·호출만 한다. 크롤링·스크래핑·주기적 동기화·빌드 시점 데이터 생성·자체 저장소 승격 단계가 없어 `external-data-ingestion.md`의 "일반적인 내부 API 조회만 하고 별도 수집·정규화·승격 단계가 없으면 이 모드를 켜지 않는다" 조건에 정확히 해당한다.

## Functional Requirements

### Must Have (MVP)
- [ ] REQ-F-001 로그인(회원번호 + 비밀번호)
  - Given 비로그인 상태로 앱에 진입, When 회원번호와 비밀번호를 입력해 제출, Then 인증 성공 시 좌석 현황 화면(PAGE-002)으로 이동한다.
  - Given 잘못된 회원번호 또는 비밀번호 입력, When 제출, Then 입력값은 유지한 채(비밀번호 필드 제외) 인라인 에러 메시지("회원번호 또는 비밀번호가 올바르지 않습니다")를 표시하고 재시도할 수 있다.
  - Given 로그인 처리 중, When 사용자가 제출 버튼을 반복 클릭, Then 버튼은 처리중 상태(disabled)로 바뀌어 중복 제출을 막는다.
  - Given 키보드만 사용하는 회원, When Tab/Enter로 입력·제출, Then 마우스 없이 로그인 흐름을 완료할 수 있다.

- [ ] REQ-F-002 오늘 날짜 좌석 현황 조회
  - Given 로그인 상태로 좌석 현황 화면 진입, When 화면이 로드되면, Then 열람실의 모든 좌석이 30분 슬롯 단위로 예약 가능/타인 예약중/내 예약/지난 시간(선택 불가) 상태로 구분 표시된다.
  - Given 오늘 모든 좌석·슬롯이 이미 예약된 상태, When 좌석 현황 화면 조회, Then "현재 예약 가능한 좌석이 없습니다" 안내와 갱신(재조회) 액션을 보여준다(빈 상태).
  - Given 열람실 전체 좌석 수만큼(정상~최대 fixture, 예: 최소 50석~최대 300석 가정) 렌더링, When 스크롤/필터 조작, Then 조작 반응이 100ms 이내 시각 피드백을 유지한다(성능 세부는 REQ-NFR-001).
  - Given 일부 좌석의 상태 조회가 실패(API 부분 실패), When 화면 표시, Then 해당 좌석은 "상태 확인 불가"로 별도 표기하고 나머지 좌석은 정상 표시한다(partial 상태).

- [ ] REQ-F-003 좌석 예약 생성
  - Given 예약 가능(available) 상태의 좌석·슬롯 선택, When 예약 확정 액션을 실행, Then 해당 좌석·슬롯이 "내 예약"으로 즉시 갱신되고 확정 피드백(인라인 메시지)을 보여준다.
  - Given 예약 확정을 시도했으나 그 사이 다른 회원이 같은 좌석·슬롯을 먼저 예약 확정(서버 409류 응답), When 확정 요청 실패 응답 수신, Then "이미 예약된 좌석입니다" 안내와 함께 좌석 현황을 최신 상태로 자동 재조회하고 내 선택은 초기화한다(동시성 충돌).
  - Given 예약 요청 중 네트워크 타임아웃, When 응답이 없음, Then 로딩 상태를 유지하다 일정 시간 후 재시도 안내를 표시하고, 중복 예약 요청을 보내지 않는다.
  - Given 키보드만 사용하는 회원, When Tab/Enter/Space로 좌석·슬롯 선택 및 확정, Then 마우스 없이 예약을 완료할 수 있다.

- [ ] REQ-F-004 예약 취소 (destructive)
  - Given 본인의 활성 예약이 있는 좌석, When 취소 액션을 실행하고 확인 다이얼로그에서 확정, Then 예약이 취소되고 해당 좌석·슬롯이 다시 예약 가능 상태로 표시된다.
  - Given 취소 확인 다이얼로그가 열린 상태, When 다이얼로그를 닫거나 취소를 선택, Then 예약 상태는 변경되지 않고 포커스가 취소 버튼(트리거)으로 복귀한다.
  - Given 취소 요청이 실패(네트워크/서버 오류), When 실패 응답 수신, Then 예약 상태를 되돌리지 않고(낙관적 갱신 금지) 실패 안내와 재시도 수단을 제공한다.

- [ ] REQ-F-005 세션 만료/미인증 접근 가드
  - Given 세션이 만료된 상태로 좌석 현황 화면에서 조작(조회/예약/취소) 시도, When API가 인증 실패(401류)를 반환, Then 로그인 화면으로 유도하고 "다시 로그인해주세요" 안내를 표시한다.
  - Given 로그인하지 않은 사용자가 좌석 현황 URL로 직접 진입, When 페이지 로드, Then 로그인 화면으로 리다이렉트된다.

### Should Have
- [ ] 좌석 현황 자동 갱신(주기적 재조회 또는 사용자 수동 새로고침 버튼) — 헛걸음 방지라는 핵심 가치를 강화하지만 폴링 주기·실시간 방식은 NEEDS_DECISION(운영 API의 polling 부하 허용치 불명).
- [ ] 좌석 검색/구역 필터(열람실이 넓어 좌석 수가 많을 경우 구역별 보기) — 좌석 수 규모가 확정되지 않아 ASSUMPTION(검증: 실제 좌석 수 확인 후 50석 이상이면 필요).

### Could Have (later phases)
- [ ] 자주 앉는 좌석 즐겨찾기/최근 예약 좌석 우선 노출
- [ ] 남은 이용 시간 카운트다운 표시

### Won't Have (this release)
- 관리자 화면(좌석/회원/정책 관리) — 사용자 명시 범위 제외
- 결제/과금 — 사용자 명시 범위 제외
- 알림(푸시/문자/이메일) — 사용자 명시 범위 제외
- 미래 날짜(내일 이후) 예약 — 사용자 요청이 "오늘 날짜"로 한정
- 대기열(waitlist)/예약 대기 신청 — 요청에 근거 없음, 범위 확장 방지
- 노쇼(no-show) 자동 처리 UI — 정책 자체가 NEEDS_DECISION/BLOCKER(아래), 알림도 범위 밖이라 이번 릴리스에서 표시만 최소화

## Non-functional Requirements
- REQ-NFR-001 Performance: 측정 환경 = 모바일 브라우저, 일반 LTE/4G 회선 가정. baseline: 로그인 완료 후 좌석 현황 화면 진입 시점부터 예약 확정 피드백까지 60초 이내(성공 조건). normal fixture = 좌석 약 50~150석, max fixture = 약 300석에서도 그리드 조작이 100ms 이내 시각 반응을 유지한다.
- REQ-NFR-002 Responsive: 모바일 우선(주 사용 기기), 태블릿/데스크톱은 보조 지원으로 레이아웃이 깨지지 않아야 한다.
- REQ-NFR-003 Accessibility: WCAG 2.2 AA. 좌석 그리드의 터치 타깃 44×44px 이상, 좌석 선택·예약·취소 전 과정 키보드 조작 가능, 가용성 표시는 색상 단독이 아니라 색+아이콘/패턴 이중 신호, 포커스 링은 `:focus-visible`에 표시.
- REQ-NFR-004 Browsers: 모바일 Safari(iOS 최근 2버전), Chrome Android(최근 2버전)를 1차 지원 대상으로 검증하고, 데스크톱 최신 Chrome/Safari/Edge는 보조 지원(레이아웃 깨짐 없음 수준)으로 검증한다.

## Data Review Strategy
- strategy: `mock` (Phase 1~2, UX·상태 검토 목적) → 실 연결은 `production-integration-later`로 분리
- fixtures/source and safety: 외부 API의 OpenAPI/계약 문서가 없어 실제 shape를 알 수 없다. Phase 2까지는 mock fixture로 normal(좌석 다수 가용)/empty(전체 만석)/loading/error(500·timeout)/partial(일부 좌석 조회 실패)/conflict(409류 동시성 충돌) 상태를 구성한다. mock 단계에서 production mutation은 발생하지 않는다.
- Mock→real transition: (1) 도서관 API의 OpenAPI 또는 동등 계약 문서 확보, (2) 인증 토큰 전달 방식과 CORS 허용 origin 확정, (3) 동시성 충돌 응답의 정확한 payload/status 확정, (4) 위 3가지가 확정된 뒤 tech-advisor가 연동 방식을 정하고 개발 단계에서 mock을 실 API 호출로 교체한다.

## Effort Trade-off
- rough size: `M`
- drivers: 화면 수는 적지만(로그인 1 + 좌석현황 1이 핵심) 좌석 그리드가 다뤄야 할 상태 수가 많다(가용/타인예약/내예약/지난시간/선택중/충돌/부분실패/만석/세션만료). 외부 API 계약이 없어 실통합 리스크가 크고, 동시성 처리(낙관적 갱신 금지, 충돌 후 재조회)가 필요하다.
- recommendation: `invest` (핵심 가치와 직결되는 단일 flow) — 단, production 연결은 계약 확보 전까지 `split`한다. Phase 1~2(기획·디자인·mock 프로토타입)는 지금 진행하고, 실 API 연동은 별도 milestone으로 분리한다.
- smallest visible review: 좌석 그리드 화면 1개를 mock 데이터로 — 가용/내예약/타인예약/충돌/만석 상태를 모두 포함한 프로토타입.
- production integration delta: mock 검토 대비 추가 노력 = 인증 토큰 처리, CORS 설정, 실제 409 응답 파싱·재시도 정책, API 장애/timeout에 대한 방어 로직. 계약 확보 전에는 추정 불가.

## Open Decisions

- ASSUMPTION: 열람실은 단일 공간(구역 구분 없음)으로 가정한다. 검증 방법: 도서관 운영팀에 열람실 수·구역 구성 확인. 복수 열람실이면 좌석 현황 화면에 열람실 선택이 추가되어야 한다.
- 결정(PC-005): 예약 취소는 confirm 다이얼로그로 처리한다(즉시 실행+undo 대신). 근거: 취소 즉시 해당 좌석이 다른 회원에게 재선점될 수 있어(헛걸음이 많다는 pain 자체가 높은 수요를 시사) undo가 항상 성공한다고 보장할 수 없다. 검증 방법: Phase 2 프로토타입에서 취소 흐름 사용성 확인.
- ASSUMPTION: 성공 조건 "1분"의 측정 시작점은 "좌석 현황 화면 진입 시점(로그인 완료 후)", 종료점은 "예약 확정 피드백 표시 시점"으로 정의한다. 근거: 로그인 소요시간(비밀번호 재설정 등)은 앱이 통제할 수 없는 변수라 핵심 지표에서 분리하는 것이 합리적. 검증 방법: Phase 2 prototype에서 task timing 측정.
- ASSUMPTION: 세션 인증 토큰은 클라이언트 메모리/세션 스토리지에만 보관하고 새로고침 시 재인증이 필요할 수 있다고 가정한다. 검증 방법: 실 API 계약 확보 후 재확인(BLOCKER 참고).
- ASSUMPTION: 브랜드 색상/로고 미지정, 다크모드 불필요, 밀도는 표준으로 가정한다(시안 확정 대상). 검증 방법: Phase 2 발산 조사 후 커밋한 단일 시안의 프리뷰 승인에서 확정.

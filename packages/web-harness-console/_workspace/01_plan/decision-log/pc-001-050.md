## PC-006 (2026-08-06) — 제한된 append-only Change Request write boundary

- Trigger: Preview를 검토한 사용자가 기획·TC·디자인을 함께 수정 요청하고 기준점과 version intent를 이력으로 남겨야 한다는 요구
- Decision: PC-002의 read-only 원칙은 정본 Source/Plan/Design과 Preview에 계속 적용한다. Console은 전용 POST endpoint를 통해 `_workspace/01_plan/change-requests/CHG-*.md` 새 파일만 exclusive-create할 수 있다.
- Integrity: 서버가 선택 Feature·TC·문서·preview digest를 현재 index에서 다시 계산한다. 기존 문서 overwrite, 임의 path, 요청 상태 전이, 승인/version 발행은 허용하지 않는다.
- Security: loopback origin 검증, JSON content type, explicit intent header, bounded body, idempotency key, symlink/realpath boundary를 적용한다.
- Versioning: 최초 요청은 `PROPOSED`와 `patch|minor|major` intent만 기록한다. 승인된 `design-v*`는 후속 변경 사이클에서 발행한다.
- Approval: 사용자의 “동의해”, “진행해” 요청 (2026-08-06)

## PC-007 (2026-08-06) — Preview FEAT/TC drawer를 변경 요청의 주 진입점으로 확정

- Trigger: 사용자가 Preview에서 시나리오를 읽는 바로 그 side panel에 변경 요청 버튼을 요구

- Boundary: iframe은 append-only endpoint를 직접 호출하지 않으며 Source/Plan/Design/Preview write 권한을 얻지 않는다. direct preview에서는 안전한 Console parent가 없으므로 action을 노출하지 않는다.
- Approval: 사용자의 “preview에서 사이드에 시나리오 나오는 곳에 버튼 변경 요청 추가” 요청 (2026-08-06)

## PC-008 (2026-08-06) — Codex 실행은 impact와 apply를 분리한 L2 연결

- Trigger: 사용자가 등록된 Change Request를 실제 Codex 수정 작업에 연결하도록 요청
- Decision: 공식 non-interactive `codex exec` adapter를 사용하되 `impact(read-only)`와 `apply(workspace-write)`를 별도 session과 별도 사용자 action으로 분리한다.
- Connection fallback: CLI binary/version/login status를 server에서 probe하고 미설치·미인증이면 실행 button을 비활성화하고 복구 안내를 표시한다.
- Security: browser는 phase와 server-issued ownership 정보만 제출한다. cwd, prompt, command, argv, model, sandbox, environment는 server가 고정한다. danger-full-access, add-dir, automatic retry, commit/push/PR/deploy는 제공하지 않는다.
- Audit: run event와 bounded structured result는 `_workspace/03_dev/codex-runs/*.jsonl`에 append-only로 남기고 00/01/02 document index에는 포함하지 않는다.
- Approval: 사용자의 “연결해줘. 만약 연결이 안되어 있다면?” 요청과 직전 합의한 영향 범위 확인 후 실행 흐름 (2026-08-06)

## PC-009 (2026-08-06) — READY_FOR_REVIEW 검토 결정은 apply-run-bound append-only event

- Trigger: 사용자가 READY_FOR_REVIEW 카드에 승인·수정 요청·변경 폐기 선택 action이 없음을 확인하고 구현을 요청
- Decision: 원본 Change Request와 Codex run audit은 변경하지 않는다. `_workspace/03_dev/change-request-decisions/<CHG>.jsonl`에 exact apply run ID, 결정, 사유, 시각을 append-only로 기록한다.
- Revision: `REVISION_REQUESTED` 사유는 다음 별도 L2 apply 승인에서 server-generated prompt의 untrusted feedback으로만 전달한다. 새 apply 결과는 새 검토 대상이 된다.
- Discard boundary: 기존 direct workspace-write run에는 독립 candidate patch가 없으므로 `DISCARDED`는 결과를 채택하지 않는 terminal review 상태다. 자동 Git restore/reset은 하지 않으며 파일 복원은 격리 후보 패치 도입 전까지 별도 작업이다.
- Integrity: loopback Origin/intent/media/idempotency, current request/latest apply ownership, READY_FOR_REVIEW transition, terminal run block을 server에서 검증한다.
- Approval: 사용자의 “진행해줘” 요청 (2026-08-06)

## PC-010 (2026-08-06) — 승인된 CHG는 기존 FEAT의 append-only revision으로 투영

- Trigger: 승인된 Change Request를 기존 FEAT에 직접 연결해 기능 관점에서 변경 이력을 확인하려는 요구
- Decision: 정본 `feature-plan.md`에 CHG ID를 매번 삽입하지 않는다. exact apply-run-bound 승인 event의 immutable `featureLinks` snapshot과 Change Request를 join해 `Feature.approvedChanges[]` read model을 파생한다.
- Integrity: 새 apply output은 영향 FEAT/Sub Feature/TC와 최종 digest를 구조화한다. 승인 시 target 포함, current catalog ownership, digest 일치를 검증한다. legacy output은 request context fallback임을 `request-context-legacy`로 표시한다.
- Navigation: Features 상세은 승인 이력에서 Changes의 CHG로 이동하고 Changes Target은 Feature/Sub Feature 상세로 돌아간다.
- Identity: 호환 변경은 기존 FEAT ID의 revision으로 누적한다. 별도 기능 대체/supersede identity 정책은 후속 major-change 범위다.
- Approval: 사용자의 “다음 작업 진행해줘” 요청 (2026-08-06)

## PC-011 (2026-08-06) — Apply는 격리 candidate 생성, review 승인이 정본 승격

- Trigger: 전체 평가에서 direct workspace-write 때문에 `DISCARDED`가 파일 복원을 보장하지 못하는 P0 운영 위험을 확인하고 사용자가 우선순위대로 진행 요청
- Decision: Codex apply cwd를 정본 project root에서 server-created temporary candidate snapshot으로 이동한다. 완료 결과는 서버가 diff한 bounded manifest/file bundle이며 review 전 정본은 바뀌지 않는다.
- Promotion: `APPROVED`만 whole-project base digest를 current와 비교한 뒤 changed file bundle을 적용한다. post-apply digest가 candidate와 다르면 touched file backup으로 복원하고 decision을 기록하지 않는다.
- Revision/Discard: `REVISION_REQUESTED|DISCARDED`는 정본 mutation/restore를 수행하지 않는다. revision은 같은 current baseline에서 새 candidate를 만든다.
- Compatibility: PC-008/009 시기의 legacy direct apply audit은 candidate가 없음을 명시하고 기존 approval/discard 경계를 유지한다.
- Boundary: `.git`, dependency/build/cache와 Console audit/candidate directory는 snapshot에서 제외하고 symlink·unsafe relative path·file/byte budget 초과는 typed BLOCKED로 거부한다.
- Approval: 사용자의 “진행해줘” 요청 (2026-08-06)

## PC-012 (2026-08-06) — Feature planning과 Console 탐색의 Page Group 도입

- Trigger: 기획 단계에서 생성된 FEAT를 페이지 대분류로 관리하고 Console Features에서도 같은 구조로 확인하려는 요청

- UI: 페이지 label/ID/route/FEAT count heading 아래 기존 FEAT/Sub Feature tree를 그대로 배치한다. 선택/hash/detail/Preview/Change Request 계약은 바꾸지 않는다.
- Approval: 사용자의 “기획 단계에서 생성된 feat 문서를 페이지 단위로 대분류 … Console에서도 그룹핑” 요청 (2026-08-06)

- Trigger: Page Group과 FEAT/TC 상세이 길어지며 Features 전체 document 높이가 과도하게 늘어난 문제
- Decision: 905px 이상에서 FeatureList와 FeatureDetail은 Console header·tabs·section heading을 제외한 남은 viewport를 같은 높이로 채우고 각각 독립 세로 스크롤한다.

## PC-014 (2026-08-06) — Apply 전 Change Request 수정은 append-only revision

- Trigger: 영향도 분석의 전제가 잘못된 경우 실제 변경 적용 전 요청사항을 정정할 수 있어야 한다는 요구
- Decision: 최초 `CHG-*.md`와 target context는 불변으로 두고 제목·요청·사유·기대 동작·version intent만 `change-request-revisions/CHG-*-REV-NNN.md`에 append-only로 추가한다. Console read model과 Codex prompt는 최신 revision을 effective request로 사용한다.
- Invalidation: 각 Codex run은 시작 시 effective request SHA-256 digest와 revision ID를 고정한다. revision 이후 이전 impact는 STALE이며 server가 digest 불일치 apply를 typed 409로 거부한다.
- Lifecycle: 수정은 active run과 apply 시작 전까지만 허용한다. candidate 생성 이후의 변경은 기존 READY_FOR_REVIEW `수정 요청` loop를 사용해 candidate audit을 보존한다.
- Security: endpoint는 same loopback Origin, explicit `revise-change-request` intent, JSON, UUID idempotency, exact CHG ownership과 lifecycle을 검증한다. 원본 rewrite, target 변경, 자동 Codex 실행은 하지 않는다.
- Approval: 사용자의 “실제 변경 요청 전까지는 반영이 안된 것이므로 요청사항을 수정” 요구 (2026-08-06)

## PC-015 (2026-08-07) — 승인 전 Change Request는 취소 이력 없이 물리 삭제

- Trigger: 정본에 반영되지 않은 Change Request를 취소 상태로 누적하지 않고 작업 목록에서 완전히 제거하려는 요구
- Decision: `APPROVED` 정본 승격 전이고 active Codex run이 없으면 사용자 확인을 거쳐 CHG 원본과 연결 revision·run audit·review decision·미승인 candidate를 함께 물리 삭제한다. tombstone, `CANCELLED` event, 취소 사유는 만들지 않는다.
- Boundary: `APPROVED` 요청과 active run은 typed conflict로 거부한다. 삭제 대상은 서버가 검증한 exact project/CHG 소유 artifact에 한정하며 transaction rollback으로 부분 삭제를 방지한다.
- UX: Changes 카드에 eligibility 기반 `삭제` action을 표시하고 확인 후 카드·count·selection을 즉시 갱신한다. 취소 시 삭제하지 않고 focus를 복원한다.
- Approval: 사용자의 “변경 요청 전에는 변경점 반영이 안된거라 그냥 삭제” 요구 (2026-08-07)
